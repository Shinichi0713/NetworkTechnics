HTTPダイジェスト認証（Digest Access Authentication）とは、Webサーバーとクライアント（ブラウザ）の間で、**パスワードをそのまま送らずに本人確認を行う認証方式**です。

一言で言えば、「**パスワードをそのまま送らず、暗号学的な「証明書」だけを送る安全な入館証明**」です。


### 基本認証との違い

HTTPにはもっと単純な「基本認証（Basic認証）」もありますが、決定的な違いがあります。

| | **基本認証（Basic）** | **ダイジェスト認証（Digest）** |
|---|---|---|
| **パスワードの送信** | **Base64エンコードのみ**（中身は丸見え） | **ハッシュ値のみ**送信（元のパスワードは出ない） |
| **セキュリティ** | 低い（盗聴されるとパスワードが漏れる） | 比較的高い（ハッシュ値だけでは元が分からない） |
| **HTTPSなし** | 非常に危険 | それでもパスワードそのものは保護できる |

### ダイジェスト認証の仕組み（簡易版）

1. **クライアントがページを要求**する
2. **サーバーが「nonce（ワンタイムの乱数）」を発行**する（「この値を使え」という一時的な鍵）
3. **クライアントは「パスワード＋nonce＋その他情報」をMD5などでハッシュ化**し、そのハッシュ値（ダイジェスト）をサーバーに送る
4. **サーバーも同じ計算をし**、送られてきたハッシュ値と一致すれば認証成功

> **例え：** 「パスワードそのものを見せる」のではなく、「パスワードと今日の合言葉を混ぜて作った印章だけを見せる」イメージです。印章だけでは元のパスワードは分かりません。


### 主な特徴

- **チャレンジ・レスポンス方式**：サーバーが毎回違うnonceを出すため、同じハッシュ値を盗んでも**再送攻撃（リプレイ攻撃）が難しい**
- **パスワードが平文で流れない**：ネットワーク上に平文パスワードが出ない
- **RFC 7616**で標準化（以前はRFC 2617）

### 注意点・限界

- **MD5は現代では脆弱**：元のRFCではMD5を使っていたが、現在はSHA-256など強固なハッシュへ移行が推奨されています
- **中間者攻撃には依然として弱い**：HTTPS（TLS）なしで使うと、通信内容そのものの改ざんは防げない
- **現代の主流は「フォーム認証＋HTTPS」**：ダイジェスト認証よりも、Cookie＋セッション＋TLSの組み合わせが一般的


### まとめ

> **HTTPダイジェスト認証＝「パスワードそのものを送らず、ハッシュ値（ダイジェスト）で本人を証明するHTTPの認証方式」**

- 基本認証より安全（平文パスワードが流れない）
- チャレンジ・レスポンスでリプレイ攻撃も一定程度防ぐ
- ただし現代では**HTTPS＋フォーム認証が主流**で、ダイジェスト認証はレガシーな用途や特殊な環境で使われることが多い
