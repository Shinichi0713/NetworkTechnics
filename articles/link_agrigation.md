組織にひかれている通信線は通信量が増減することがあります。
業績がよく、突然フロアの人員が増加したり、インターネットを頻繁に利用する部門が移籍してくると、従来あった通信線では通信量が賄いきれなくなることがあるかもしれません。

こんな時に通信線を引きなおすということは手になります。
ですが、通信線を引きなおさなくても大丈夫にする技術があります。

今回扱うのはそんな通信量の増減に対応することが出来る技術・リンクアグリゲーションについて説明していきます。

## 概要

リンクアグリゲーションとは、**複数の物理的なネットワークケーブルを束ねて、1つの論理的な太い回線として扱う技術**です。

### 主なメリット

- **帯域の増大**：1Gbpsのポートを4本束ねれば、4Gbpsとして使える
- **冗長化**：1本が断線しても、残りの回線で通信が継続される
- **STPによるブロックを回避**：複数線を「1本の論理線」として見せるため、スパニングツリーに余分な線としてブロックされず、全ポートを同時に使える

## 必要となった背景

リンクアグリゲーションが必要となった理由は、主に以下の3つです。

### 1. ポート速度の壁を低コストで突破したかった
サーバーとスイッチ間の通信量が増えた際、「1Gbpsのポートをより高速な10Gbpsポートに置き換える」という方法は、**NICやスイッチの交換コストが高く、既存機器との互換性も失われます**。そこで、**既存の1Gbpsポートを複数束ねる**ことで、安価に帯域を増やす手段として生まれました。

### 2. STPのせいで冗長リンクが「眠っていた」
冗長化のために複数ケーブルを繋いでも、STP（スパニングツリー）が有効だと**ループ防止のため一部ポートがブロックされ、実際には1本しか使えません**。リンクアグリゲーションは、複数物理回線を**論理的に1本**として扱うためSTPにブロックされず、**全ポートを同時に活用しながら冗長化**できます。

### 3. ケーブル1本の障害でサービスが止まるのを防ぐため
サーバー・ストレージ・コアスイッチなど、**途絶えてはならない重要な接続**では、1本のケーブル断線が致命傷になります。複数本を束ねておけば、1本が抜けても通信が継続されるため、高可用性が確保できます。


## 仕組みの概要

リンクアグリゲーションの仕組みは、**複数の物理回線を1つの論理回線として『まとめ』、そこに流れる通信を各回線に『振り分ける』** という2段階の仕組みです。

以下、順を追って説明します。

### 1. まとめる：論理ポート（LAG）の形成

スイッチやサーバーの複数ポートを1つのグループ（**LAG：Link Aggregation Group**、または**ポートチャネル**）に設定します。

```
[サーバー]                      [スイッチ]
 eth1 ───────┬─────────────── Gi0/1
             │                 Gi0/2
 eth2 ───────┴─────────────── Gi0/3
             
 4本の物理線 → 「Port-channel1」という1本の論理線として見える
```

この状態で、OSやスイッチからは「Port-channel1」という**1つのインターフェース**として認識されます。IPアドレスもこの論理ポートに付与します。

### 2. 交渉する：LACP（Link Aggregation Control Protocol）

両端の機器が「本当に束ねてもいいですか？」と確認し合うプロトコルが **LACP（IEEE 802.3ad）** です。

- **Activeモード**：自らLACPパケットを送って相手に交渉を求める
- **Passiveモード**：LACPパケットを待ち受ける（相手がActiveなら交渉成立）

両端の設定（速度、デュプレックス、VLANなど）が一致したポートだけがLAGに加わります。不一致のポートは除外（**サスペンド**）されるため、誤設定による混乱を防げます。

### 3. 振り分ける：負荷分散（ハッシュ計算）

LAGに入ったパケットは、**「どの物理線を使うか」** を決める必要があります。ここで**ハッシュ計算**が使われます。

__よく使われるハッシュ要素__
- 送信元MACアドレス
- 宛先MACアドレス
- 送信元IPアドレス
- 宛先IPアドレス
- 送信元ポート番号（L4）
- 宛先ポート番号（L4）

```
例：パケットA（PC→サーバー）
  送信元IP + 宛先IP + ポート番号 → ハッシュ値(1) → "eth1の線を使う"

例：パケットB（別のPC→同じサーバー）
  送信元IP + 宛先IP + ポート番号 → ハッシュ値(3) → "eth2の線を使う"
```

**重要なポイント**：
- **同じ通信（フロー）は必ず同じ物理線を通ります**。これにより、パケットの順序が逆転するのを防ぎます。
- 逆に言うと、**1つの通信（例：1ファイル転送）は1本の線しか使えません**。全体としては複数線を使っていても、個別の通信が1本に集中するとその線がボトルネックになることがあります。

### 4. 壊れたら：障害時の動作

束ねた線のうち1本が断線（またはエラー過多）になると：

1. LACPが障害を検知（または物理層の断を検知）
2. そのポートをLAGから**自動的に除外**
3. 残りの正常な線だけで通信を継続
4. 断線前にその線を使っていたフローは、ハッシュ再計算で別の正常線に移動

この切り替えは**秒以下**で行われ、TCPセッションなども継続されます。

### 5. STPから見たリンクアグリゲーション

前回説明したSTPの文脈と繋げると：

- リンクアグリゲーションで束ねた回線は、**STPからは「1本のリンク」** として見えます
- そのため、4本束ねていてもSTPはブロックしません
- **全ポートを同時に転送に使いながら、冗長性も確保できる**のが最大のメリットです


### STPとの関係

リンクアグリゲーションで束ねられた回線は、**STPからは「1本のリンク」として見えます**。そのため、通常の独立した冗長リンクのようにブロードキャストストームでブロックされることはなく、**全ての物理回線を有効に使いながら冗長性も確保**できます。

## リンクアグリゲーションを有するL2SW

現代の業務用L2スイッチにとってリンクアグリゲーションは「特別な高級機能」ではなく、**「標準装備の基本機能」** です。
ただし、搭載されているからと言って、**最大何グループまで作れるか**、**LACPと静的LAGのどちらに対応しているか**は機種により異なるため、設計時の確認は必要です。

### どの程度「標準」か？

- **企業・業務向けL2スイッチ**（Cisco、Aruba、Juniper、NEC、Yamaha等）：  
  ほぼ**100%近くがリンクアグリゲーション（LACP）に対応**しています。設定画面（CLIやWeb）で`channel-group`や`port-channel`、`LAG`といった項目が見られるはずです。

- **家庭用・SOHO向けアンマネージドスイッチ**（設定画面なしの安価機器）：  
  基本的に**非対応**です。ポートを単に増やすだけの機器なので、LAGの設定概念自体がありません。

### なぜ「特別ではなくなった」のか

1980〜90年代の初期イーサネットスイッチでは、リンクアグリゲーションは**高級機やレイヤー3スイッチに限られた特別な機能**でした。しかし以下の理由で一般化しました。

1. **ASIC（スイッチング専用チップ）の進化**  
   複数ポートを1つの論理ポートとして扱い、ハッシュ計算で振り分ける処理が、現代のASICでは**ごく標準的な機能**として実装コストが劇的に下がりました。

2. **標準化の完成（IEEE 802.3ad / 802.1AX）**  
   ベンダー間の相互接続が容易になり、どのメーカーの機器でもLACPで束ねられるようになりました。

3. **帯域需要の増大**  
   1Gbpsが当たり前になり、10Gbpsへの全ポート移行が高価なため、**1Gbps×4本で4Gbps確保**という現実的な解が必須となり、エントリー機にも搭載されるようになりました。

### 技術的に「特別」だった点（歴史的には）

リンクアグリゲーションが初めて登場した頃は、以下の点で特別でした。

- **MACアドレステーブルの特殊扱い**：同じ論理ポートに複数の物理ポートが属するため、MACアドレスの学習・転送テーブルを論理ポート単位で管理する必要があった
- **フレーム順序の保証**：同じフローを同じ物理線に固定するハッシュロジックが必要
- **LACPの状態管理**：両端の交渉状態を監視し、異常ポートを自動除外する制御が必要

これらは現在では**L2スイッチの基本機能セット**として当たり前に組み込まれています。

## 総括

リンクアグリゲーションの本質は、**「STPが『塞ぐ』ことで解決したループ問題を、『束ねて1本に見せる』ことで解決しつつ、帯域増大と冗長化を同時に実現する、物理回線の抽象化技術」** です。

もう少し分解すると、以下の3つの本質に集約されます。

__1. STPとは逆のアプローチで「ループの悪影響」を無力化する__

STPは「余分な回線を論理的に塞ぐ」ことでループを防ぎますが、リンクアグリゲーションは「複数回線を**最初から1本の論理回線**として定義することで、STPにブロックされることなく、かつループとして認識されないようにする」。つまり、**「塞がずに統合する」** ことで、全ポートを有効活用します。

__2. 速度の壁を「金ではなく、論理で」突破する__

より高速なポート（10G→40G→100G）へ逐次移行するのは高コストです。リンクアグリゲーションは、**既存のポートを「数で殴る」** ことで、安価に帯域をスケールさせる現実的な解です。これは「物理的制約を、論理的な再定義で回避する」発想です。

__3. フロー単位の分離と統合の両立__

複数の物理線を1本に見せながらも、内部では**フロー単位で線を固定**することで「パケット順序の逆転」というレイヤー2の大前提を崩さない。つまり、**外からは1本、中では複数、でも同じ会話は同じ線** という、整合性と効率を両立させた制御が核心です。


一言で表せば、**リンクアグリゲーションは「複数の物理回線を1つの論理的回線に抽象化し、STPに縛られずに帯域と耐久性を両立させる、コスト意識に満ちたネットワークの集約技術」** です。
