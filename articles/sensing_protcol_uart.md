マイコンなどのコンピューティングデバイスとセンサーを接続するときに、そんな通信で計測値をマイコンに渡すかという知見が必要となります。
そして、そんな通信ルールの中にはSPI、1-Wireなどのプロトコルが存在し、うち、代表例として挙げられるのがUARTです。

本日はそんなUARTについて説明していきます。

## 概要

UARTは、**2本の線（TX・RX）で、1対1の非同期シリアル通信**を行うプロトコルです。

### 一言で言うと

**「クロック線を使わずに、事前の速度合意だけでデータを送り合う、最もシンプルな有線通信方式」** です。

### 仕組みのイメージ

2人の人が、**目覚まし時計を見ないで**手紙を1文字ずつ交換すると想像してください。

- 双方が「**1秒に1文字送る**」と事前に約束しておく（これが**ボーレート**）
- 相手も同じ速度で読む
- 手紙の束の先頭に「これから始めます」合図（**スタートビット**）
- 最後に「終わりです」合図（**ストップビット**）

クロック線がないため、この「速度の約束」を守ることが通信成立の鍵になります。

### 配線

| 信号線        | 役割             |
| ------------- | ---------------- |
| **TX**  | 送信（Transmit） |
| **RX**  | 受信（Receive）  |
| **GND** | 共通接地（必須） |

TXとRXは**交差**して接続します（AのTX → BのRX、AのRX → BのTX）。

### 特徴

| 項目                  | 内容                                                        |
| --------------------- | ----------------------------------------------------------- |
| **同期/非同期** | 非同期（クロック線不要）                                    |
| **通信形態**    | 1対1のみ                                                    |
| **速度**        | 9600bps ~ 1Mbps程度（典型的には115200bps）                  |
| **配線本数**    | 最小3本（TX・RX・GND）                                      |
| **強み**        | シンプル、長距離にも比較的強い、実装が容易                  |
| **弱み**        | 1対1のみ、速度はSPI等より遅い、ボーレートの不一致で文字化け |

## 開発背景

UARTは、**コンピュータが周辺機器や遠隔地と「手軽に」通信する必要性**から生まれました。以下、その歴史的な背景を整理して説明します。

### 1. 生まれた時代背景（1960年代）

1960年代、コンピュータは大型のメインフレームでした。当時の課題は以下の通りです。

- **周辺機器**（テレタイプライタ、紙テープ読み取り機、プリンタ）と接続したい
- **遠隔地のコンピュータ**や端末と通信したい
- しかし、**同期用のクロック線を引くのは高価で不便**（特に電話回線を使う場合）

当時の通信インフラは**電話回線**が主流でした。電話回線は元々音声用に設計されており、クロック信号を送るための追加配線を持っていませんでした。そのため、「クロック線なしでデータを送る」仕組みが求められました。

### 2. RS-232規格の登場（1962年）

アメリカの電子工業会（EIA）が **RS-232** 規格を制定しました。

- これは**電圧レベル**（±3V〜±15Vなど）や**ピン配列**を標準化したものです
- モデム（MODEM）を介して電話回線経由で通信することを想定
- この規格に従って、コンピュータとモデムを接続する必要がありました

ただし、RS-232は「物理的な配線規格」であり、**データの送受信タイミング自体を制御する回路**が別途必要でした。そこで登場したのがUARTです。

### 3. UARTチップの登場（1970年代）

初期のコンピュータでは、シリアル通信を**ソフトウェアでビットを叩いて**（ビットバンギング）行っていました。しかしこれには大きな問題がありました。

- **CPU負荷が極めて高い**
- **タイミングが不正確**（高速化が困難）
- **パリティチェックやフレーミングの処理が煩雑**

そこで、1970年代に **UART専用の集積回路（IC）** が登場しました。

| 年代         | 代表的なUARTチップ                                    |
| ------------ | ----------------------------------------------------- |
| 1970年代初頭 | Western Digital TR1402、General Instruments AY-5-1013 |
| 1970年代中盤 | Texas Instruments TMS6011、SMC COM2502                |
| 1980年代     | National Semiconductor INS8250（PC用）、後に16550A    |

これらのチップは以下の処理を**ハードウェアで自動化**しました。

- パラレルデータをシリアルデータに変換（送信）
- シリアルデータをパラレルデータに変換（受信）
- スタートビット・ストップビットの付加と検出
- パリティチェック

### 4. なぜ「非同期」だったのか

同期通信（SPIやI2Cのようにクロック線を共有）と比較して、UARTの非同期方式には当時ならではのメリットがありました。

| 同期通信の課題                   | UART（非同期）の解決策             |
| -------------------------------- | ---------------------------------- |
| クロック線が必要（配線コスト増） | クロック線不要（2本で通信）        |
| 長距離通信でクロックが歪む       | 各文字ごとにスタートビットで再同期 |
| 電話回線ではクロックを送れない   | ボーレートの事前合意だけで通信可能 |

電話回線のような**帯域が限られ、クロックを送れない媒体**で通信するために、非同期方式は最適な選択でした。

### 5. 現在への繋がり

今日でもUARTは広く使われています。

- **USB-UART変換チップ**（FT232、CP2102、CH340等）により、USBポートから簡単にUART信号を取り出せる
- **マイコン**（Arduino、ESP32、STM32等）にはUARTペリフェラルが標準搭載
- **GPS、Bluetooth、WiFiモジュール**等のセンサ・通信モジュールがUARTインターフェースを採用

つまり、UARTは「電話回線時代に生まれた古い技術」ですが、その**シンプルさと堅牢性**から、現代の組み込み開発でも依然として不可欠なプロトコルです。

### よく使われる場面

- **GPSモジュール**とマイコンの通信
- **Bluetoothモジュール**（HC-05等）との接続
- PCとの**デバッグ出力**（シリアルモニタ）
- **LiDAR・距離センサ**等のデータ受信

## 通信原理

UARTの通信原理を、**信号の流れ**から**ビットレベルの動作**まで順を追って説明します。

### 1. 基本

> **「クロックを共有しない代わりに、『これからデータを送ります』という合図（スタートビット）でタイミングを合わせ、あらかじめ約束した速度（ボーレート）で1ビットずつ送受信する」**

これがUARTの通信原理の全てです。

### 2. 直感的なアナロジー

2人が、**目覚まし時計なしで**手紙を1文字ずつ交換すると想像してください。

1. **事前の約束**: 「1秒に1文字ずつ、順番に送ります」（これがボーレート）
2. **合図**: 相手が「はじめます」と言った瞬間（これがスタートビット）を起点にタイミングを開始
3. **文字の交換**: 合図から1秒後、2秒後、3秒後...と決まった間隔で1文字ずつ送る
4. **終わりの合図**: 最後に「おしまいです」と伝える（これがストップビット）

重要なのは、**途中で時計を見なくても、合図の瞬間から自分の心拍（ボーレート）を刻み続ければ、相手の文字を正しく読める**という点です。

### 3. フレーム構造（ビットレベル）

UARTは**1フレーム**と呼ばれる単位でデータを送ります。

```
        Start    D0      D1      D2      D3      D4      D5      D6      D7     Stop
          │      │       │       │       │       │       │       │       │       │
TX line:  ▼      ▓▓      ▓▓      ▓▓      ▓▓      ▓▓      ▓▓      ▓▓      ▓▓      ▲
        (LOW)   (LSB)                                   (MSB)            (HIGH)
```

| 要素                     | 内容                      | 役割                                                                 |
| ------------------------ | ------------------------- | -------------------------------------------------------------------- |
| **スタートビット** | 常にLOW (0)               | 「これからデータを送る」合図。受信側はこれを検出してタイミングを開始 |
| **データビット**   | 5〜9ビット（通常8ビット） | 実際のデータ。LSB（最下位ビット）から順に送信                        |
| **パリティビット** | オプション（偶数/奇数）   | エラーチェック用。1フレーム内の1の数を調整                           |
| **ストップビット** | 常にHIGH (1)、1〜2ビット  | 「フレーム終了」の合図。次のスタートビットを待つ                     |

### 4. 受信側の動作原理（再同期の仕組み）

受信側はクロックを持っていますが、送信側のクロックとは別物です。そのため、**スタートビットの立下りエッジ（HIGH→LOW）を検出して再同期**します。

__受信側のステップ__

1. **アイドル状態**: RX線はHIGHを監視
2. **スタートビット検出**: HIGH→LOWの変化を検出。これを「ビット中央」としてタイミングを開始
3. **ビット中央でのサンプリング**: ボーレート周期の1.5倍、2.5倍、3.5倍...のタイミングでRX線を読み取る
4. **ストップビット確認**: HIGHを確認したらフレーム完了

```
RX line:  HIGH   LOW    D0=1    D1=0    D2=1    ...
              ↑
          立下り検出（ここからタイミング開始）
               └─1T─┘
                    ↑ サンプリング（D0中央）
                         ↑ サンプリング（D1中央）
                              ↑ サンプリング（D2中央）
```

### 5. なぜ「再同期」で問題が起きないのか

クロックには誤差があります。例えば、送信側が115200bps、受信側も115200bpsと設定していても、実際にはわずかにずれます。

しかし、UARTは**1フレーム（最大11ビット程度）の間だけタイミングを維持**すればよいため、以下の誤差なら問題ありません。

```
許容誤差 ≈ 1 / (2 * フレームビット数) ≈ 1/22 ≈ 4.5%
```

実際には、UARTのボーレート生成回路（UART周辺クロック / ボーレート）の分周比の関係で、**±2%〜±3%以内**に収めることが推奨されています。

### 6. ボーレートの計算例

マイコンのクロックが16MHzの場合、115200bpsを生成するには:

```
分周比 = 16,000,000 / 115,200 = 138.888...
```

分周比は整数でなければならないため、実際には139を使います。

```
実際のボーレート = 16,000,000 / 139 = 115,107 bps
誤差 = (115,200 - 115,107) / 115,200 ≈ 0.08%
```

これは±2%以内なので、十分に通信可能です。

### 7. 通信原理のまとめ

| 項目                           | 内容                                                            |
| ------------------------------ | --------------------------------------------------------------- |
| **同期方式**             | 非同期（クロック線不要）                                        |
| **タイミングの合わせ方** | スタートビットの立下りエッジで再同期                            |
| **データの読み取り**     | ボーレート周期の中央でサンプリング                              |
| **誤差許容**             | 1フレーム内なら約±2%〜±3%まで許容                             |
| **フレーム構成**         | スタートビット + データ + パリティ(オプション) + ストップビット |

## 未だに利用される理由

UARTが半世紀以上経った今も使われ続けている理由は、**「シンプルさがもたらす実用性」** にあります。以下に整理します。

### 1. 配線が極めてシンプル

| プロトコル     | 必要な信号線（最小）                      |
| -------------- | ----------------------------------------- |
| **UART** | **TX・RX・GND の3本**               |
| I2C            | SDA・SCL・GND の3本（プルアップ抵抗追加） |
| SPI            | MOSI・MISO・SCLK・CS・GND の5本+          |
| USB            | D+・D-・VBUS・GND の4本（プロトコル複雑） |

- 基板上の配線が少ないほど、**基板面積・コスト・故障率**が減る
- コネクタのピン数も少なくて済む
- 特に小型デバイス・低コスト製品ではこの差は大きい

### 2. 実装が容易（ハード・ソフト両面）

__ハードウェア面__

- クロック線がないため、**配線長の制約が緩い**
- プルアップ抵抗も不要（I2Cや1-Wireと異なり）
- マイコンにはほぼ必ずUARTペリフェラルが内蔵されている

__ソフトウェア面__

- 初期化は「ボーレートを設定するだけ」で済む
- I2Cのようなアドレス管理や、SPIのようなCS線管理が不要
- デバッグ出力（`printf`的な使い方）に最適

```
// UART初期化（Arduino例）- これだけ
Serial.begin(115200);
```

### 3. デバッグ・開発に不可欠

組み込み開発において、UARTは**事実上の標準的なデバッグ手段**です。

- プログラムの動作状況をPCのシリアルモニタに出力
- センサ値をリアルタイムで確認
- エラーログの出力

多くのマイコン開発環境では、UART経由のシリアル出力が**最も手軽なデバッグ方法**として最初から組み込まれています。

### 4. USBとの親和性が高い

現代のPCには物理的なUARTポート（RS-232のD-Sub9ピン）はほぼなくなりましたが、**USB-UART変換IC**（FT232、CP2102、CH340等）により、USBポートから簡単にUART信号を取り出せます。

- USBの複雑なプロトコルを理解しなくても、PCとマイコンがUARTで通信できる
- ドライバが普及しており、OS標準または簡単にインストール可能
- ブレッドボード上の回路でも、USB-UARTモジュール1つでPC接続が完了

### 5. モジュール・センサとの親和性

多くの市販モジュールがUARTインターフェースを採用しています。

| デバイス                       | 用途                 |
| ------------------------------ | -------------------- |
| GPSモジュール                  | 位置情報のNMEA出力   |
| Bluetoothモジュール（HC-05等） | 無線シリアル通信     |
| WiFiモジュール（ESP-01等）     | ATコマンドによる制御 |
| LiDAR・距離センサ              | 距離データ出力       |
| GSM/LTEモジュール              | 携帯回線通信         |

これらのモジュールは「電源を入れてTXから読むだけ」で使えるシンプルさが魅力です。

### 6. 長距離通信に強い（RS-485との組み合わせ）

UARTそのものは短距離向けですが、**RS-485トランシーバ**と組み合わせることで:

- 数百m〜1km以上の長距離通信が可能
- 差動信号によりノイズに強い
- 産業用センサーネットワークで広く使用

UARTのシンプルなフレーム構造を活かしながら、物理層だけを強化できるのも利点です。

### 7. 非同期方式の「弱点」が現代では問題にならない

かつての課題であった「ボーレートの精度」は、現代では解決されています。

- マイコンのクロック精度が向上（水晶発振子・PLL）
- UARTペリフェラルにボーレート生成回路が内蔵
- ±2%以内の誤差は容易に達成可能

つまり、非同期方式の弱点が現代の技術で十分にカバーされているため、**メリットだけが残っている**状態です。

## 総括

UARTとは、クロック線を使わず、ボーレートという速度の約束だけでデータを送り合う、最もシンプルな通信方式です。1960年代の電話回線通信の課題から生まれ、配線の少なさと実装の容易さがゆえに、現代のマイコン・センサ・デバッグ出力において今もなお、最も身近に使われ続けているプロトコルです。
