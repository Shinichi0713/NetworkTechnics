インターネット黎明期は通信の安全性ということがしっかり考えられていませんでした。
そのため、常にデータの内容が盗み見られるリスクがついて回っていた訳です。
そんな通信のリスクを改善したプロトコルがTLSと呼ばれるものです。
本日はそんなTLSについて説明していきます。

## 概要

TLS（Transport Layer Security）は、インターネット上でデータを **「盗み見られない」「途中で改ざんされていない」** と確信できるように送るための、通信の「防犯システム」です。[TLSの定義](https://www.cloudflare.com/learning/ssl/transport-layer-security-tls/) HTTPSの「S」や、メールの暗号化などで使われています。

### 1. 例え：封筒と鍵

TLSをなしで通信するのは、**「住所だけ書いたハガキ」** を送るようなものです。途中の誰でも中身を読めます。

TLSありで通信するのは、**「開けるには専用の鍵が必要な封筒」** に入れて送るようなものです。

- **封筒を作る**：送り先専用の鍵でしか開けないようにする（暗号化）
- **封筒に署名する**：「本物の送り主からです」と証明する（認証）
- **中身が改ざんされていないか確認**：封筒に封印をして、開けたら破れるようにする（改ざん検知）

### 2. 仕組み：2つの鍵を使い分ける

TLSでは、効率と安全性を両立するため、**2種類の鍵**を使い分けます。[TLSハンドシェイクの仕組み](https://www.cloudflare.com/learning/ssl/what-happens-in-a-tls-handshake/)

__① ハンドシェイク（手を組む段階）：公開鍵暗号方式__

通信を始めるとき、サーバーは「公開鍵（みんなに見せる鍵）」と「秘密鍵（自分だけが持つ鍵）」のペアを持っています。

1. クライアント → サーバー：「通信を始めたい」
2. サーバー → クライアント：「これが私の公開鍵と身分証明書（証明書）です」
3. クライアント：「証明書を確認して、本物のサーバーだと分かった」
4. クライアント → サーバー：「では、この共通鍵を公開鍵で暗号化して送ります」

これで、**共通鍵（セッション鍵）** が安全に両者間で共有できました。

__② 実際の通信：共通鍵暗号方式__

ハンドシェイク後は、共有された共通鍵でデータを暗号化して送り合います。

- **公開鍵暗号**：安全だが遅い → 鍵の交換だけに使う
- **共通鍵暗号**：速いが鍵の配送が問題 → データのやり取りに使う

この「公開鍵で共通鍵を送り、共通鍵で本番通信をする」という工夫が、TLSの核心です。

### 3. TCPとの関係

TCPが「確実に届ける」仕組みなら、TLSは「**届く途中で中身を覗かれない**」仕組みです。

| レイヤー | 役割 |
|---------|------|
| アプリケーション層（HTTPなど） | 実際のデータの内容 |
| **TLS層** | **暗号化・復号・改ざん検知** |
| TCP層 | 確実なデータ転送 |
| IP層 | パケットの配送 |

TLSはTCPの上に乗ります。だから「HTTP over TLS over TCP」がHTTPSです。

### 4. TLSの進化

| バージョン | 特徴 |
|-----------|------|
| SSL 3.0（旧名） | 1996年。TLSの前身だが、現在は脆弱性により使用不可 |
| TLS 1.2 | 2008年。広く使われたが、ハンドシェイクが複雑で遅い |
| **TLS 1.3** | **2018年**。[RFC 8446](https://www.rfc-editor.org/info/rfc8446/)で標準化。ハンドシェイクを大幅に簡略化（1-RTT）。不要な暗号スイートを削除し、安全性と速度を向上 |

TLS 1.3は、QUIC（前回説明したTCPに代わるプロトコル）とも深く関係しています。QUICは「TLS 1.3の暗号化機能を内部に統合」することで、接続確立と暗号化を同時に行っています。[TLS 1.3とQUICの関係](https://blog.cloudflare.com/rfc-8446-aka-tls-1-3/)

### 5. 境界：HTTPとHTTPSの違い

| 項目 | HTTP | HTTPS |
|------|------|-------|
| 暗号化 | なし（平文） | あり（TLS） |
| ポート番号 | 80 | 443 |
| 改ざん検知 | なし | あり |
| 身元確認 | なし | サーバー証明書で確認 |

## 開発された経緯

TLSの開発経緯は、現在のインターネット商取引の基盤となった**SSL（Secure Sockets Layer）** から始まります。以下、歴史的な流れを追って説明します。

### 1. 背景：Webの普及と「安全な通信」の必要性

1990年代初頭、World Wide Webが普及し始めると、オンラインショッピングやオンラインバンキングなど、**クレジットカード番号やパスワードを送る必要があるサービス**が登場しました。しかし、当時のHTTP通信は平文（暗号化なし）であり、途中でデータを盗み見られたり改ざんされたりするリスクがありました。[SSL/TLSの歴史](https://www.nic.ad.jp/ja/newsletter/No59/0800.html)

この「Web上で安全に通信する仕組み」が急務となり、Netscapeが先駆けて開発に取り組みました。

### 2. SSLの誕生（1994〜1995年）

**Netscape Communications**は、自社のブラウザ（Netscape Navigator）で安全な通信を実現するため、**SSL（Secure Sockets Layer）** というプロトコルを設計・開発しました。[TLSのWikipedia](https://ja.wikipedia.org/wiki/Transport_Layer_Security)

| バージョン | 時期 | 特徴 |
|-----------|------|------|
| SSL 1.0 | 開発中止 | 深刻なセキュリティ上の欠陥があり、公開されず |
| **SSL 2.0** | **1995年** | 初の公開版。しかし後に複数の脆弱性が発見 |
| **SSL 3.0** | **1995年** | SSL 2.0の問題を修正した大幅な改良版 |

SSL 3.0は後のTLSの基礎となりましたが、2014年の**POODLE攻撃**などの脆弱性が発見され、現在は使用が推奨されていません。[SSL 3.0 RFC](https://tex2e.github.io/rfc-translater/html/rfc6101.html)

### 3. なぜ「SSL」から「TLS」に変わったのか

SSLはNetscapeという**一企業が独自に開発したプロトコル**でした。インターネットの標準技術として広く普及させるためには、**中立的な標準化団体による標準化**が必要でした。

そこで、**IETF（Internet Engineering Task Force）** がSSL 3.0を基に、より汎用的で標準化されたプロトコルを策定しました。これが**TLS（Transport Layer Security）** です。[SSL/TLSの歴史](https://www.nic.ad.jp/ja/newsletter/No59/0800.html)

__名前が変わった理由__

- **SSL**はNetscapeの商標であり、他社が自由に実装・標準化するには障害がありました。
- **TLS**という名前に変えることで、**ベンダー中立のオープン標準**として位置づけられました。

### 4. TLSの標準化と進化

| バージョン | 年 | 内容 |
|-----------|-----|------|
| **TLS 1.0** | **1999年** | [RFC 2246](https://tex2e.github.io/rfc-translater/html/rfc2246)として標準化。SSL 3.0をベースに改良。 |
| TLS 1.1 | 2006年 | セキュリティ脆弱性への対処 |
| **TLS 1.2** | **2008年** | 暗号スイートの拡充、ハッシュアルゴリズムの改良 |
| **TLS 1.3** | **2018年** | [RFC 8446](https://www.rfc-editor.org/info/rfc8446/)として標準化。ハンドシェイクの簡略化、古い脆弱な暗号機能の削除 |

TLS 1.0は「SSL 3.0と大きく変わらない」設計でしたが、以降のバージョンではセキュリティと性能が段階的に強化されていきました。

### 5. SSLとTLSの関係：なぜ今でも「SSL」と呼ばれるのか

技術的には「SSL」は古いプロトコルで、現在の標準は「TLS」です。しかし、以下の理由で一般には「SSL/TLS」や「SSL証明書」といった呼び方が残っています。[TLSのWikipedia](https://ja.wikipedia.org/wiki/Transport_Layer_Security)

- SSLという名前が最初に広く普及した
- 証明書業界や企業が「SSL証明書」という呼称を商標・商習慣として継続
- TLSはSSLの「直系の後継」であり、概念的に同一視されることも多い

## 仕組み

TLSの詳細な仕組みを、現行標準である**TLS 1.3**を中心に、段階的に説明します。

### 1. TLSが提供する3つの保護機能

TLSは以下の3つを同時に実現します。

| 保護内容 | 意味 | 実現方法 |
|---------|------|---------|
| **機密性** | 盗み見られない | 暗号化 |
| **完全性** | 途中で改ざんされていない | MAC（メッセージ認証コード） |
| **認証** | 相手が本物である | デジタル証明書 |


### 2. 暗号化の仕組み：2つの鍵方式の協働

TLSでは「公開鍵暗号」と「共通鍵暗号」を組み合わせます。

__公開鍵暗号（非対称鍵暗号）__

- **公開鍵**：誰にでも配布してよい鍵。暗号化に使う。
- **秘密鍵**：サーバーだけが持つ鍵。復号に使う。

「公開鍵で暗号化したデータは、その公開鍵に対応する秘密鍵でしか復号できない」という性質を利用します。

__共通鍵暗号（対称鍵暗号）__

- 送受信者が**同じ1つの鍵**を共有し、それで暗号化・復号を行う。
- 公開鍵暗号に比べて**数百〜数千倍速い**。

__なぜ2つを使い分けるのか__

| 方式 | 強み | 弱み |
|------|------|------|
| 公開鍵暗号 | 鍵を安全に交換できる | 遅い |
| 共通鍵暗号 | 速い | 鍵の配送が難しい |

TLSでは、**公開鍵暗号で「共通鍵」を安全に交換し、その後は共通鍵暗号で実際のデータ通信を行う**という「ハイブリッド方式」を採用しています。

### 3. ハンドシェイク：TLS 1.3の詳細

TLS 1.3では、接続確立にかかる往復回数が**1-RTT**（1往復）に短縮されました。以下、ステップごとに見ていきます。

__前提：鍵交換の方式（ECDHE）__

TLS 1.3では、主に**ECDHE**（Elliptic Curve Diffie-Hellman Ephemeral）という鍵交換方式を使います。これは以下の特徴を持ちます。

- クライアントとサーバーが、それぞれ**一時的な鍵ペア**を生成
- お互いの公開鍵を交換するだけで、**同じ共通鍵**を導出できる
- 「一時的（Ephemeral）」なので、**過去の通信を復号できない**（前方秘匿性）

__ステップ1：ClientHello（クライアント → サーバー）__

クライアントが以下を送信します。

- 対応するTLSバージョン
- **鍵交換用の公開鍵（key_share）**：「私が生成した一時的な公開鍵です」
- 対応する暗号スイート（暗号化アルゴリズムの組み合わせ）リスト
- ランダムな値（Random）

```
ClientHello
├── Version: TLS 1.3
├── Random: [32バイトの乱数]
├── Cipher Suites: [AES-256-GCM-SHA384, ...]
└── key_share: [クライアントのECDHE公開鍵]
```

__ステップ2：ServerHello + 暗号化されたハンドシェイク（サーバー → クライアント）__

サーバーが以下を返します。

- 選んだ暗号スイート
- **サーバーの鍵交換用公開鍵（key_share）**
- 証明書と証明書検証（暗号化済み）

この時点で、両者はお互いのECDHE公開鍵を持っているため、**同じ「ハンドシェイク秘密鍵（Handshake Secret）」** を導出できます。

```
ServerHello
├── Version: TLS 1.3
├── Random: [32バイトの乱数]
├── Cipher Suite: AES-256-GCM-SHA384
└── key_share: [サーバーのECDHE公開鍵]
```

__ステップ3：鍵導出（Key Schedule）__

TLS 1.3では、**HKDF（HMAC-based Key Derivation Function）** という関数を使って、Handshake Secretから複数の鍵を導出します。

```
Early Secret（0-RTT用）
    ↓
Handshake Secret（ハンドシェイク鍵）
    ↓
Master Secret（アプリケーションデータ鍵）
```

導出される鍵の種類：

| 鍵の名前 | 用途 |
|---------|------|
| **client_handshake_traffic_secret** | クライアント→サーバーのハンドシェイク暗号化 |
| **server_handshake_traffic_secret** | サーバー→クライアントのハンドシェイク暗号化 |
| **client_application_traffic_secret** | クライアント→サーバーのアプリケーションデータ暗号化 |
| **server_application_traffic_secret** | サーバー→クライアントのアプリケーションデータ暗号化 |

__ステップ4：Finishedメッセージ（両方向）__

ハンドシェイクの最後に、両者が**Finished**メッセージを送り合います。これは、これまでのハンドシェイクの全メッセージをハッシュ化したものを、導出した鍵で暗号化したものです。

- 相手が「同じ鍵を正しく導出できたか」を確認
- ハンドシェイクが改ざんされていないことを検証

### 4. 証明書と認証の仕組み

サーバーが「本物であること」を証明するために、**X.509デジタル証明書**を使います。

__証明書の内容__

| 項目 | 内容 |
|------|------|
| **Subject** | サーバーの識別情報（ドメイン名、組織名など） |
| **Issuer** | 証明書を発行した認証局（CA） |
| **Public Key** | サーバーの公開鍵 |
| **Signature** | CAによるデジタル署名 |
| **Validity Period** | 有効期限 |

__信頼の連鎖（チェーン）__

```
[ルートCA証明書] ← ブラウザにプリインストール済み
    ↓ 署名
[中間CA証明書]
    ↓ 署名
[サーバー証明書（example.com）]
```

クライアントは、サーバー証明書が「信頼できるCA」によって署名されているかを検証します。これが**PKI（Public Key Infrastructure）** の仕組みです。

### 5. データ転送：AEAD暗号化

ハンドシェイク後、アプリケーションデータは**AEAD（Authenticated Encryption with Associated Data）** という方式で暗号化されます。

TLS 1.3で使われる主なAEAD暗号スイート：

| 暗号スイート | 内容 |
|-------------|------|
| **TLS_AES_256_GCM_SHA384** | AES-256-GCM（暗号化）+ SHA-384（ハッシュ） |
| **TLS_CHACHA20_POLY1305_SHA256** | ChaCha20-Poly1305（モバイル向け高速暗号） |

AEADの特徴：

- **暗号化と改ざん検知を同時に行う**
- 復号時に「改ざんがあればエラーになる」
- TLS 1.2までの「暗号化とMACを別々に行う」方式の脆弱性を排除

### 6. セッション再開：0-RTT

TLS 1.3では、以前接続したことがある場合、**0-RTT**（ゼロ・ラウンド・トリップ・タイム）でデータを送ることができます。

__仕組み__

1. 初回接続時に、サーバーから**PSK（Pre-Shared Key）** を受け取る
2. 次回接続時、クライアントはPSKと**Early Data**（アプリケーションデータ）をClientHelloと同時に送信
3. サーバーはPSKを検証し、即座にデータを処理

```
【0-RTT】
クライアント ──ClientHello + Early Data──→ サーバー
クライアント ←────Application Data──────── サーバー
```

__0-RTTの注意点：リプレイ攻撃のリスク__

0-RTTは高速ですが、**同じデータを攻撃者が再送信（リプレイ）する攻撃**に対して脆弱です。したがって、0-RTTでは「冪等性（同じ処理を何度しても結果が変わらない）」が保証されるリクエスト（GETなど）に限定して使うべきとされています。

### 7. 前方秘匿性（Forward Secrecy）

ECDHEの「E（Ephemeral：一時的）」が意味するのは、**毎回異なる一時的な鍵ペアを使う**ということです。

- ある通信の**一時的な秘密鍵**が漏洩しても、**過去や未来の通信は復号できない**
- サーバーの**長期的な秘密鍵**（証明書の秘密鍵）が漏洩しても、**過去の通信記録は復号できない**

これが**前方秘匿性**です。TLS 1.3では、前方秘匿性を持つ鍵交換（ECDHE）が事実上必須となっています。

### 8. TLS 1.2との主な違い

| 項目 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| ハンドシェイク往復数 | 2-RTT | 1-RTT |
| ハンドシェイクの暗号化 | ServerHello以降のみ | ServerHello以降の大部分 |
| 対応暗号スイート数 | 多く（脆弱なものも含む） | 少なく（安全なもののみ） |
| 前方秘匿性 | オプション | 事実上必須 |
| 圧縮 | あり（CRIME攻撃の原因） | なし |
| 0-RTT | なし | あり（PSKベース） |

## TCPとの関係

TCPとTLSは、インターネット通信において「**別々の仕事を分担しながら、上下に重なって協力する**」関係です。

### 1. 直感的な例え：宅配便と封筒

TCPとTLSの関係を宅配便に例えると：

- **TCP** = **宅配便の配達システム**
  - 荷物を「確実に」「順番通りに」「届け先まで」運ぶ
  - 届かなければ再送し、順番が乱れれば並べ直す

- **TLS** = **配達される箱の中の「鍵付き封筒」**
  - 箱自体（TCP）は普通に運ばれる
  - でも箱の中身は鍵付き封筒に入っていて、途中で開けられない

つまり、**TLSはTCPの上に乗り、TCPが届けた「箱」の中身を暗号化・保護する**のです。

### 2. レイヤーでの位置関係

インターネットの通信は「層（レイヤー）」に分かれています。TCPとTLSは隣り合う層に位置します。

```
┌─────────────────────────────┐
│  アプリケーション層          │  ← HTTP、SMTP、FTPなど
│  （「何を送るか」を決める）    │
├─────────────────────────────┤
│  TLS層                      │  ← 「中身を暗号化・復号する」
│  （「安全に送る」ための加工）  │
├─────────────────────────────┤
│  トランスポート層（TCP）      │  ← 「確実に届ける」
│  （「どうやって届けるか」）    │
├─────────────────────────────┤
│  インターネット層（IP）        │  ← 「どこへ届けるか」
│  （「宛先まで運ぶ」）          │
└─────────────────────────────┘
```

__データの流れ（送信時）__

1. アプリケーションが「HTTPリクエスト」を作る
2. **TLS層がそのデータを暗号化**する
3. **TCP層が暗号化されたデータを「確実に」届ける**（セグメント化、シーケンス番号、ACK、再送制御）
4. IP層がパケットを宛先まで運ぶ

__データの流れ（受信時）__

1. IP層がパケットを受け取る
2. **TCP層が順番を整え、欠けがあれば再送を求めて「確実なデータ」を復元**
3. **TLS層がそのデータを復号**する
4. アプリケーションが復号されたHTTPリクエストを読む

### 3. なぜTCPとTLSは「分離」されているのか

TCPとTLSが一体化していないのには、明確な理由があります。

| 観点 | TCPの仕事 | TLSの仕事 |
|------|----------|----------|
| **目的** | 確実なデータ転送 | データの機密性・完全性・認証 |
| **対象** | バイト列（中身は関知しない） | アプリケーションデータ（中身を暗号化） |
| **設計思想** | 「届ける」ことに特化 | 「守る」ことに特化 |
| **独立性** | TLSなしでも動く（HTTPなど） | TCPなしでは動かない（TLSはTCPの上に乗る） |

この分離により、以下の柔軟性が生まれます。

- TCPだけを使いたい場合：暗号化が不要な内部ネットワーク通信など
- TCP + TLSを使いたい場合：HTTPS、SMTPSなど、安全な通信が必要な場合
- TCPの代わりにUDP + QUICを使う場合：TLS相当の機能がQUIC内部に統合

### 4. TCPとTLSの連携：ハンドシェイクの重ね合わせ

TCPとTLSは、それぞれ「接続確立のハンドシェイク」を持っています。これらは**順番に重ね合わさって**行われます。

```
【TCPの3ウェイ・ハンドシェイク】
クライアント ──SYN───────→ サーバー
クライアント ←──SYN+ACK──── サーバー
クライアント ──ACK───────→ サーバー
        ↓
   TCP接続確立完了！
        ↓
【TLSのハンドシェイク（TLS 1.3の場合）】
クライアント ──ClientHello────────→ サーバー
クライアント ←──ServerHello + 証明書── サーバー
クライアント ──Finished + 暗号化データ──→ サーバー
        ↓
   TLSセッション確立完了！
        ↓
【アプリケーションデータの送受信】
クライアント ⇄ サーバー（暗号化されたHTTPなど）
```

つまり、**TCPが「道」を作り、TLSが「道の上を安全に運ぶためのルール」を追加する**イメージです。

### 5. 境界：TCPなしでTLSは使えないのか

原則として、TLSは「信頼できる転送層」の上で動作する設計です。現在のインターネットでは以下のパターンがあります。

| 組み合わせ | 用途 | 備考 |
|-----------|------|------|
| **TCP + TLS** | HTTPS、SMTPS、IMAPSなど | 最も一般的 |
| **UDP + DTLS** | IoT、VoIP、VPNなど | TLSをUDP上で動作させた版 |
| **UDP + QUIC（TLS 1.3統合）** | HTTP/3 | TLSがQUIC内部に組み込まれている |

DTLS（Datagram TLS）は、UDPのような「信頼性のない」プロトコルの上でTLSの機能を提供するために作られました。ただし、TCPほど普及しているわけではありません。

## 近年の動向

TLSは現在、以下の主要な課題に直面しており、それぞれ活発に研究・標準化が進められています。

### 1. 量子コンピュータによる既存暗号の破壊リスク（ポスト量子暗号：PQC）

**課題：** 現在のTLSが使うECDHEやRSAは、十分に大規模な量子コンピュータが実現すれば**Shorのアルゴリズム**により破壊可能です。過去に記録された暗号化通信が「今から復号される（Harvest Now, Decrypt Later）」リスクがあります。

**研究・対応：**
- NISTが2024年に**ML-KEM**（鍵共有）と**ML-DSA/SLH-DSA**（署名）をPQC標準として制定
- IETFではTLSへのPQC統合ドラフト（[draft-wagner-tls-keysharepqc](https://datatracker.ietf.org/doc/html/draft-wagner-tls-keysharepqc-00)）が検討中
- 現行暗号とPQCを併用する**ハイブリッド構成**が移行期の主流となる見込み
- PQCの鍵・署名サイズが大きい（数KB〜数十KB）ため、TLSハンドシェイクのパケットサイズ増大が課題


### 2. プライバシーと監視の葛藤（ECH：Encrypted Client Hello）

**課題：** 従来のTLSではClientHello内の**SNI（Server Name Indication）**が平文で送信され、通信先のドメイン名が途中のISPや監視者に漏洩していました。

**研究・対応：**
- **ECH（Encrypted Client Hello）** がRFC 9849（2026年3月）として標準化。ClientHello全体を暗号化し、通信先ドメインを隠蔽
- しかし、ISPや企業のセキュリティ監視、親告なりフィルタリングが困難になるという反論もあり（[ECH Considered Harmfulドラフト](https://www.ietf.org/archive/id/draft-stein-tls-ech-considered-harmful-00.txt)）
- 検閲回避に悪用される可能性も指摘され、プライバシーとセキュリティ・規制のバランスが議論中

### 3. 証明書とPKIの信頼性問題

**課題：** TLSの認証は**X.509証明書＋PKI（認証局）** に依存していますが、不正なCAによる証明書発行、CAの侵害、証明書の有効期間が長すぎる問題があります。

**研究・対応：**
- 証明書の有効期間短縮化（90日への移行議論）
- **CT（Certificate Transparency）ログ**の義務化による監視強化
- 分散型・ブロックチェーンベースの代替PKIの研究（ただし実用化には至っていない）

### 4. パフォーマンスとPQCの両立

**課題：** PQCアルゴリズムは従来のECDHEに比べて計算コスト・通信量が大きく、特にIoTやモバイル環境ではリソース制約が問題になります。

**研究・対応：**
- 軽量PQCアルゴリズムの探索
- ハイブリッド鍵交換の最適化
- サーバー負荷軽減のための鍵共有キャッシュ戦略

### 5. 0-RTTのリプレイ攻撃リスク

**課題：** TLS 1.3の0-RTTは高速だが、**リプレイ攻撃**に対して本質的に脆弱。同じリクエストを攻撃者が再送信できる。

**研究・対応：**
- 0-RTTの使用を「冪等な操作（GETなど）」に限定するベストプラクティスの策定
- リプレイ検知メカニズムの研究
- 「PQCロック」機能の提案：PQCが有効なサイトで古い暗号へのロールバックを防ぐ仕組み

## 総括

TLSは、インターネット上の通信を「盗み見られない」「改ざんされない」と保証するための暗号化プロトコルです。HTTPSの「S」やメールの暗号化などで使われています。

**仕組みの核心**は、公開鍵暗号で「共通鍵」を安全に交換し、その後は高速な共通鍵暗号で実際のデータ通信を行うというハイブリッド方式です。現行のTLS 1.3では、1往復（1-RTT）で接続確立と暗号化が完了し、さらに0-RTTによる再接続高速化も可能です。

**TCPとの関係**は、TCPが「確実に届ける」土台を作り、TLSが「届く途中の中身を守る」加工層としてTCPの上に乗るというものです。HTTP over TLS over TCPがHTTPSです。

**歴史**は、1990年代にNetscapeが開発したSSLから始まり、1999年にIETFがベンダー中立の標準としてTLSを策定しました。現在のTLS 1.3（2018年）は、ハンドシェイクの高速化と脆弱な暗号機能の削除により、安全性と性能を大幅に向上させています。

**現在の課題**として、量子コンピュータによる暗号破壊リスクへの対応（ポスト量子暗号PQCの統合）、通信先ドメインの漏洩を防ぐECH（Encrypted Client Hello）の普及、証明書・PKIの信頼性確保などが研究・標準化の最前線にあります。
