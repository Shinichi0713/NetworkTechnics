**DNSフォワーダ（DNS Forwarder）** とは、**DNSクライアントからの名前解決要求を受け取った際に、自分で再帰的に解決するのではなく、別のDNSサーバー（上位のフルサービスリゾルバーや特定のDNSサーバー）に問い合わせを転送し、その結果をクライアントに中継する機能・サーバー**のことです。

## 1. 本質：「自分で解決しないで、誰かに丸投げするDNSサーバー」

通常のDNSサーバー（フルサービスリゾルバー）は、ルートサーバー→TLDサーバー→権威サーバーと順に辿って自分で解決します。フォワーダは**その「再帰的解決作業」を上位サーバーに委譲**します。

```
【フルサービスリゾルバー（自分で解決する場合）】
[PC] → "www.example.com のIPを教えて"
          ↓
[フルサービスリゾルバー] → ルートDNS → TLD DNS → 権威DNS
          ↓
[PC] ← "93.184.216.34 です"

【DNSフォワーダ（上位に転送する場合）】
[PC] → "www.example.com のIPを教えて"
          ↓
[DNSフォワーダ] → "お客様、こちらの解決お願いします"
          ↓
[上位フルサービスリゾルバー] → ルートDNS → TLD DNS → 権威DNS
          ↓
[DNSフォワーダ] ← "93.184.216.34 です"
          ↓
[PC] ← "93.184.216.34 です"
```

> **本質は、「再帰的な名前解決の負荷と管理を上位サーバーに集約し、自サイト・自組織では軽量な転送のみを行う」ことです。**

---

## 2. なぜDNSフォワーダを使うのか

### ① キャッシュの集約と効率化

組織内に複数のPCがある場合、それぞれがインターネット上のDNSサーバーに直接問い合わせると、**同じドメインへの問い合わせが何度も発生**します。

フォワーダを1台置くと、**フォワーダが結果をキャッシュ**しておき、次に同じ問い合わせが来たらキャッシュから即座に応答できます。

```
[PC-A] → "www.google.com?" → [DNSフォワーダ] → 上位DNS
[PC-B] → "www.google.com?" → [DNSフォワーダ] → キャッシュヒット！即応答
[PC-C] → "www.google.com?" → [DNSフォワーダ] → キャッシュヒット！即応答
```

### ② ファイアウォール・セキュリティポリシーの簡素化

社内の全PCがインターネット上の任意のDNSサーバー（UDP 53番ポート）に直接アクセスできると、**ファイアウォールの管理が複雑**になります。

フォワーダを使うと、**「DNS問い合わせを外部に出せるのはフォワーダだけ」**という設計が可能になり、セキュリティが向上します。

```
【フォワーダなし】
PC-A, PC-B, PC-C ... 全端末 → インターネットDNS（任意のIP:53）へ直接接続
                              ↑ 管理が大変、フィルタリングも困難

【フォワーダあり】
PC-A, PC-B, PC-C → [DNSフォワーダ:53] → 指定された上位DNS:53のみ
                        ↑
                   ここだけ外部DNSへのアクセスを許可すればよい
                   不正なDNSサーバーへの接続をブロックしやすい
```

### ③ 内部DNSと外部DNSの分離

企業ネットワークでは、**社内専用のドメイン（例：intranet.company.local）**と**インターネットのドメイン**の両方を使います。

フォワーダを使うと以下のような**条件付きフォワーディング**が可能です。

| 問い合わせの対象           | 転送先                                                   |
| -------------------------- | -------------------------------------------------------- |
| `*.company.local`        | 社内の権威DNSサーバー                                    |
| `*.corp.internal`        | 社内の別のDNSサーバー                                    |
| それ以外（インターネット） | ISPのDNS or Google DNS (8.8.8.8) or Cloudflare (1.1.1.1) |

```
[PC] → "server01.corp.internal のIPを教えて"
          ↓
[DNSフォワーダ] → 「.corp.internal は社内DNSサーバーに転送」
          ↓
[PC] ← "10.0.5.20 です"

[PC] → "www.yahoo.com のIPを教えて"
          ↓
[DNSフォワーダ] → 「インターネット宛ては Cloudflare に転送」
          ↓
[PC] ← "202.165.... です"
```

## 3. DNSフォワーダの主な実装例

| 実装                            | 特徴                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------- |
| **dnsmasq**               | 軽量。多くのLinuxルーター・OpenWrtで使用。DHCPサーバー機能も兼ねることが多い |
| **BIND** (named)          | `forwarders` 設定でフォワーダとして動作可能。企業・ISPで広く使われる       |
| **Windows Server DNS**    | 「フォワーダ」タブで上位DNSサーバーを設定。Active Directory環境で標準的      |
| **Unbound**               | 検証リゾルバーだが、フォワーダモードも可能。セキュアで軽量                   |
| **家庭用ルーター内蔵DNS** | ほとんどがdnsmasqベースのフォワーダ。ISPのDNS or ユーザー設定DNSに転送       |

## 4. フォワーダとフルサービスリゾルバーの違い

| 項目                       | DNSフォワーダ                                              | フルサービスリゾルバー                        |
| -------------------------- | ---------------------------------------------------------- | --------------------------------------------- |
| **解決の仕方**       | 上位サーバーに転送して結果を中継                           | ルート→TLD→権威を自分で辿る                 |
| **キャッシュ**       | 持つことが多い（必須ではない）                             | 基本的に持つ                                  |
| **負荷**             | 軽量                                                       | 再帰処理のためやや重い                        |
| **使用場所**         | 社内LAN、家庭用ルーター、ブランチオフィス                  | ISP、クラウド（8.8.8.8, 1.1.1.1）、大規模企業 |
| **セキュリティ機能** | 単なる転送が基本だが、フィルタリングを付加できる場合もある | DNSSEC検証などを行える                        |

## 5. これまでの文脈との接続

これまでの会話のネットワーク技術とDNSフォワーダを結びつけると、以下のようになります。

- **OSPF/BGPの文脈**：企業ネットワーク内でOSPFが動作し、エッジルーターがBGPでインターネットと接続する環境では、**社内のDNSフォワーダ**がインターネット側のDNSサーバー（ISPのDNSや8.8.8.8など）に問い合わせを転送する際、その通信もOSPFでルーティングされ、エッジでNATされる
- **VPCの文脈**：AWS VPCでは**Route 53 Resolver**がDNSフォワーダの役割を担い、VPC内のDNS問い合わせをRoute 53やオンプレミスのDNSサーバーに転送できる。**VPC内のEC2→Route 53 Resolver→オンプレDNS**という経路で、DNSフォワーディングがハイブリッドクラウドの重要な接続点になる
- **広域イーサネットの文脈**：拠点間がL2透過で接続されていれば、**拠点AのDNSフォワーダが拠点Bの社内DNSサーバーに直接問い合わせる**ことも可能（L3でももちろん可能）

## まとめ

> **DNSフォワーダとは、DNSクライアントからの名前解決要求を受け取り、自分で再帰的に解決せずに上位のDNSサーバーに転送して結果を中継する機能・サーバーです。キャッシュの集約による効率化、ファイアウォールポリシーの簡素化、内部DNSと外部DNSの分離（条件付きフォワーディング）などの目的で使われ、dnsmasqやBIND、Windows Server DNSなどで実装されます。本質的には「DNS解決の作業を委譲しつつ、組織内のDNSトラフィックの集約点となる」存在です。**

L2SW（Layer 2 Switch）は、**VRRPの存在自体を意識しません**。L2SWが見ているのは、**「VRRP仮想MACアドレスが、自分のどのポートで学習されたか」**だけです。

---

## 1. 核心：L2SWは「MACアドレス」で転送する

L2SWはIPアドレスやVRRPのマスター/バックアップ状態を見ることができません。L2SWはあくまで**レイヤー2（MACアドレス）の世界**で動作します。

```
【VRRP環境の構成例】
        [PC-A]
           │
      ┌────┴────┐
      │  L2SW   │
      └────┬────┘
    ┌──────┴──────┐
[L3SW-1]      [L3SW-2]
(マスター)     (バックアップ)
  10.0.0.1     10.0.0.2
  仮想IP: 10.0.0.254
  仮想MAC: 00-00-5E-00-01-01
```

---

## 2. VRRP仮想MACアドレスが鍵になる

VRRPでは、マスターに選ばれたL3SWだけが、**仮想MACアドレス**を自らのインターフェースに設定します。

| 項目                       | 内容                                                               |
| -------------------------- | ------------------------------------------------------------------ |
| **仮想IPアドレス**   | 配下のPCがデフォルトゲートウェイとして設定するIP（例：10.0.0.254） |
| **仮想MACアドレス**  | 例：`00-00-5E-00-01-{VRID}`（VRIDはVRRPグループID）              |
| **マスターL3SW**     | 仮想IP・仮想MACを実際に持ち、GARP（Gratuitous ARP）を送信する      |
| **バックアップL3SW** | 仮想MACを持たず、VRRPアドバタイズメントを待機している              |

---

## 3. フレームがマスターに届くまでの流れ

### ① PCがARP要求を送信

PCは「デフォルトゲートウェイ 10.0.0.254 のMACアドレスは？」とARP要求をブロードキャストします。

### ② マスターL3SWだけが応答

- **マスターL3SW**：「10.0.0.254 は `00-00-5E-00-01-01` です」と**仮想MACアドレス**で応答
- **バックアップL3SW**：何も応答しない

### ③ L2SWがMACアドレスを学習

L2SWは、**「`00-00-5E-00-01-01` というMACアドレスは、L3SW-1に繋がっているポートだ」**とMACアドレステーブルに学習します。

```
L2SWのMACアドレステーブル（イメージ）
┌──────────────────────┬──────────┐
│    MACアドレス        │   ポート  │
├──────────────────────┼──────────┤
│ 00-00-5E-00-01-01    │  Port 1  │  ← L3SW-1側（マスター）
│ PC-AのMAC            │  Port 5  │
└──────────────────────┴──────────┘
```

### ④ 以降のPCからの通信

PCがインターネット宛てにパケットを送信する際、**宛先MACアドレスは `00-00-5E-00-01-01`** になります。

L2SWはこの宛先MACアドレスを見て、**Port 1（L3SW-1）に転送**します。L3SW-2には一切フレームは届きません。

## 4. マスターが故障したときはどうなるか

L3SW-1が故障すると、VRRPの仕組みでL3SW-2がマスターに昇格します。

1. L3SW-2が**GARP（Gratuitous ARP）**を送信
   - 「10.0.0.254（00-00-5E-00-01-01）は、私のポートにいます」とL2SWに通知するようなARP
2. L2SWはMACアドレステーブルを**更新**
   - `00-00-5E-00-01-01` → Port 2（L3SW-2側）に書き換え
3. 以降のフレームは自動的にL3SW-2に転送される

```
【故障前】
PC-A → L2SW → L3SW-1(マスター) → インターネット
              L3SW-2(バックアップ)

【故障後】
PC-A → L2SW → L3SW-2(新マスター) → インターネット
              L3SW-1(ダウン)
```

---

## 5. まとめ

> **配下のL2SWは、VRRPのマスター/バックアップ状態を見てL3SWを選んでいるわけではありません。L2SWはあくまで「VRRP仮想MACアドレス（例：00-00-5E-00-01-01）がどのポートで学習されたか」をMACアドレステーブルで確認し、そのポートにフレームを転送するだけです。マスターL3SWだけがこの仮想MACアドレスで応答するため、結果としてフレームは常にマスターに届きます。マスターが故障してバックアップが昇格すると、GARPによってL2SWのMACアドレステーブルが更新され、以降のフレームは新マスターに転送されるようになります。**

## サブネットが交換できなくなるケース

まず**前提として、VRRPはそもそも「同じサブネット（同一L2ブロードキャストドメイン）内」でのみ動作するプロトコル**です。VRRP広告は**TTL=255のIPマルチキャスト（224.0.0.18）**として送信され、ルーターを跨ぐとTTLが減衰して**破棄される設計**になっています。つまり、**「サブネット間でVRRP情報を交換する」ことはプロトコル上不可能**です。

その上で、**「同じサブネットに属しているはずのVRRPルーター間で、VRRP広告が交換できなくなるケース」**を整理します。

---

## 1. L2経路の物理的分断（スプリットブラーン環境）

最も典型的なケースです。

```
【正常時】
[L3SW-1]──[L2SW-1]════════[L2SW-2]──[L3SW-2]
  マスター    ↑  トランク    ↑      バックアップ
         (VRRP広告がL2SW経由で届く)

【L2SW間トランクが断線した場合】
[L3SW-1]──[L2SW-1]   ×   [L2SW-2]──[L3SW-2]
  マスター                バックアップ
  ↑_________________________↑
  VRRP広告が届かない（L2分断）
```

L2SW間のトランクリンクが切断されると、L3SW-1とL3SW-2は**同じIPサブネットに属していても、L2ブロードキャストドメインが分断**されます。VRRP広告（マルチキャスト）はL3ルーターを跨げないため、お互いの広告が届かなくなります。

結果：**両方がマスターになってしまう「デュアルマスター（Split-Brain）」状態**が発生します。

---

## 2. VLANのトランクポートからの削除・設定ミス

L2SWのトランクポートから、**VRRPを設定したVLANが削除**された場合も同様です。

```
【L2SWのトランクポート設定】
ポート1（L3SW-1側）: allowed vlan 10,20
ポート2（L3SW-2側）: allowed vlan 10    ← VLAN 20 が削除されている！

→ L3SW-1とL3SW-2のVLAN 20 SVI間ではVRRP広告が交換できない
```

`switchport trunk allowed vlan` の設定ミスや、VLANの意図しないプルーニングなどが原因です。

---

## 3. ACLやセキュリティ設定によるVRRPマルチキャストのブロック

L2SWやL3SWのACLで、**VRRPのマルチキャストアドレス（224.0.0.18）やIPプロトコル番号112（VRRP）が明示的にドロップ**されている場合、広告パケットが届きません。

| 設定箇所                    | 内容                                 |
| --------------------------- | ------------------------------------ |
| **VLAN ACL（VACL）**  | VLAN内のトラフィックをフィルタリング |
| **ポートACL（PACL）** | 特定ポートの入出力をフィルタリング   |
| **ルーターACL**       | SVIインターフェースでの入力フィルタ  |

VRRPはIPプロトコル番号112を使用するため、「TCP/UDPのみ許可」という過剰に制限的なACLがあると遮断されます。

---

## 4. VRRP認証キーの不一致

VRRPには**プレーンテキストまたはAH（Authentication Header）による認証**機能があります（VRRPv2ではオプション、v3では廃止されていますが、従来の環境では使用されることがあります）。

- L3SW-1：認証キー `secret123`
- L3SW-2：認証キー `secret124`（タイポや設定漏れ）

認証キーが一致しないと、**VRRP広告パケットを相互に破棄**し、お互いを認識できません。

---

## 5. SVI（VLANインターフェース）のダウン・管理ダウン

L3SWの**SVI（Switch Virtual Interface）がダウン**している場合、VRRPプロセス自体がそのインターフェースから広告を送信できません。

SVIがダウンする原因の例：

| 原因                                         | 説明                                                       |
| -------------------------------------------- | ---------------------------------------------------------- |
| **該当VLANにアクティブなポートがない** | `vlan 20` に属するL2ポートが全てダウン → SVI 20がダウン |
| **管理ダウン**                         | `shutdown` 設定                                          |
| **依存関係の故障**                     | ハードウェア故障、ソフトウェアクラッシュ                   |

---

## 6. プライベートVLAN（Private VLAN）やポート隔離

L2SWで**プライベートVLAN**や**ポート隔離（port isolation / protected port）**が設定されていると、同じVLAN内でもポート間の通信が制限されます。

```
【ポート隔離の例】
L3SW-1 → L2SW Port 1（isolated）
L3SW-2 → L2SW Port 2（isolated）

→ Port 1とPort 2は同じVLANでも相互に通信できない
→ VRRP広告が交換できない
```

---

## 7. なぜ「サブネット間」では絶対に動かないのか

念のため、プロトコルの性質を整理します。

| 項目               | VRRPの仕様                                            |
| ------------------ | ----------------------------------------------------- |
| **宛先IP**   | 224.0.0.18（リンクローカルマルチキャスト）            |
| **TTL**      | 255（ルーターを1ホップでも跨ぐと破棄される）          |
| **L3転送**   | **不可能**。IGPのようにルーター間で広報されない |
| **動作範囲** | 同一ブロードキャストドメイン（同一サブネット）のみ    |

つまり、**VRRP広告が「サブネット間」を跨いで届くことは、プロトコル設計上ありえません**。異なるサブネット間でゲートウェイの冗長性を実現したい場合は、VRRPではなく**ルーティングプロトコル（OSPF/BGPなど）による経路冗長化**を使います。

## まとめ

> **VRRPはそもそもサブネット間では動作しないプロトコルです（TTL=255のリンクローカルマルチキャスト）。同じサブネット内でVRRP広告が交換できなくなる主なケースは、①L2SW間リンクの断線などによるL2ブロードキャストドメインの分断（スプリットブラーン）、②トランクポートからのVLAN削除、③ACLによる224.0.0.18やIPプロトコル112のブロック、④VRRP認証キーの不一致、⑤SVIのダウン、⑥プライベートVLAN・ポート隔離による通信制限、です。これらが発生すると、VRRPルーター間で広告が届かず、デュアルマスターなどの障害が生じます。**

VRRP広告が「サブネット間」を跨いで届くことは、プロトコル設計上ありえません。異なるサブネット間でゲートウェイの冗長性を実現したい場合は、VRRPではなくルーティングプロトコル（OSPF/BGPなど）による経路冗長化を使います。

## ポートフォーワーディング

**「ポートをフォワーディング（Forwarding）状態にする」**とは、**スパニングツリープロトコル（STP/RSTP/MSTP）において、そのポートが「通常のイーサネットフレームを受信・転送できる」アクティブな状態になること**です。

これは、スイッチのポートが**「ループ防止のための制限」から解放され、本格的なL2通信を開始する」**瞬間を指します。

---

## 1. STPのポート状態の全体像

スパニングツリーは、ネットワーク上のループ（ブロードキャストストーム）を防ぐため、ポートを**段階的に状態遷移**させます。

| 状態                 | フレーム転送 | MAC学習 | BPDUの送受信 | 目的                                   |
| -------------------- | ------------ | ------- | ------------ | -------------------------------------- |
| **Disabled**   | ×           | ×      | ×           | ポートが管理ダウン（shutdown）         |
| **Blocking**   | ×           | ×      | 受信のみ     | ループ防止のため、とりあえず塞ぐ       |
| **Listening**  | ×           | ×      | 送受信       | トポロジー確定待ち。BPDUを交換         |
| **Learning**   | ×           | ○      | 送受信       | MACアドレステーブルを構築開始          |
| **Forwarding** | ○           | ○      | 送受信       | **通常通りフレームを転送・学習** |

> **フォワーディング状態 = 「フレーム転送 + MAC学習 + BPDU交換」がすべて有効な、ポートとして完全に稼働している状態**

---

## 2. なぜすぐにフォワーディングにならないのか

### ループ防止のための「慎重な立ち上げ」

スイッチのポートをケーブル接続した瞬間、すぐにフレームを転送すると、**トポロジーが確定する前にループが発生**する危険があります。

```
【危険なケース：すぐに転送すると】
[SW-A]══════[SW-B]
   ╲          /
    ╲════════/
     ループ！

SW-AとSW-Bが同時にポートをForwardingにすると、
どちらかがBlockingすべきポートも転送してしまい、
ブロードキャストストームが発生
```

STPは以下の手順で**安全を確認してから**Forwardingにします。

1. **Listening状態（約15秒）**：BPDUを交換して「誰がルートブリッジか」「どのポートがBlockingか」を決定
2. **Learning状態（約15秒）**：フレームは転送しないが、届いたフレームの送信元MACを学習してMACテーブルを構築
3. **Forwarding状態**：すべての機能を解放

従来のSTP（802.1D）では、この遷移に**30～50秒**かかりました。

---

## 3. フォワーディング状態で何ができるか

ポートがForwardingになると、以下がすべて可能になります。

```
【Forwardingポートの動作】
[PC] → [SW Port 3(Forwarding)] → [SW内部] → [SW Port 1(Forwarding)] → [別のSW/ルーター]
            ↑
      ① フレームを受信する
      ② 送信元MACを学習（MACテーブルに登録）
      ③ 宛先MACを見て適切なポートに転送（またはフラッディング）
      ④ BPDUを送受信し続ける（トポロジー変化を監視）
```

---

## 4. RSTP（Rapid STP）での進化

従来STPの30～50秒の遅延は、現代のネットワークでは許容しがたいものでした。そこで**RSTP（802.1w）**では、ポートの役割と状態をより細かく判定し、**数秒以内**でForwardingに移行できるようになりました。

| STP種別                     | Forwardingまでの時間 | 仕組み                                                              |
| --------------------------- | -------------------- | ------------------------------------------------------------------- |
| **従来STP（802.1D）** | 30～50秒             | タイマー（Listening 15秒 + Learning 15秒）で固定                    |
| **RSTP（802.1w）**    | 数秒（通常1秒以下）  | ポートの役割（Edge Port / Root Port / Designated Port）を即座に判定 |
| **MSTP（802.1s）**    | RSTPと同程度         | 複数VLANに対応したRSTPの拡張                                        |

RSTPでは、**Edge Port（エンドデバイス直結ポート）**を設定すると、BPDUが届かないことを確認して**即座にForwarding**になります。

```
【RSTPの例】
[PC]──[SW Port 5: edge port] → 接続直後にForwarding
[SW-A]──[SW-B: トランク] → 役割判定後、数秒でForwarding
```

---

## 5. 以前の文脈との接続

### トランクポートとの関係

以前ご説明した**トランクポート**も、STPの対象です。トランクポートがForwardingになって初めて、**複数VLANのフレームがそのリンクを通過**できます。

```
【トランクポートがBlockingの場合】
[SW-A]──(Trunk: Blocking)──[SW-B]
→ VLAN10, VLAN20, VLAN30 すべての通信が止まる

【トランクポートがForwardingの場合】
[SW-A]══(Trunk: Forwarding)══[SW-B]
→ VLAN10, VLAN20, VLAN30 すべての通信が通る
```

### VRRPとの関係

VRRPを設定したL3SWの**SVIがUPになるためには、そのVLANに属する物理ポートがForwarding状態である必要**があります。ポートがBlockingのままでは、SVIがダウンし、VRRP広告も送信できません。

### 広域イーサネットとの関係

広域イーサネットの**事業者コア**でも、802.1ah（PBB）やMSTPの組み合わせで、**不要なリンクをBlockingし、必要なリンクだけForwarding**にすることで、ループなく冗長性を確保しています。

---

## まとめ

> **「ポートをフォワーディング状態にする」とは、スパニングツリープロトコル（STP）において、そのポートが「通常のイーサネットフレームの受信・転送・MACアドレス学習」をすべて行えるアクティブ状態になることです。ループ防止のため、ポートはBlocking → Listening → Learning → Forwardingと段階的に遷移し、トポロジーの安全性を確認してからForwardingになります。従来STPでは30～50秒かかりましたが、RSTP/MSTPでは数秒以内に移行できます。トランクポートやVRRP環境でも、このForwarding状態が通信の前提となります。**

**フォワーディング状態でない状態**は、**STP（802.1D）とRSTP（802.1w）で名称が異なります**が、いずれも**「ループ防止のため、フレーム転送を制限している状態」**です。

以下、それぞれの状態を整理します。

---

## 1. STP（802.1D）における「フォワーディングでない状態」

従来のSTPでは、**4つの非フォワーディング状態**があります。

| 状態                | フレーム転送 | MAC学習 | BPDUの処理  | 概要                                                        |
| ------------------- | ------------ | ------- | ----------- | ----------------------------------------------------------- |
| **Disabled**  | ×           | ×      | ×          | ポートが管理ダウン（`shutdown`）。意図的に無効化          |
| **Blocking**  | ×           | ×      | 受信のみ    | ループ防止のため、とりあえず塞いでいる状態。BPDUだけ受信    |
| **Listening** | ×           | ×      | 送受信      | トポロジー確定のためBPDUを交換中。まだフレームは扱わない    |
| **Learning**  | ×           | ○      | 送受信      | MACアドレステーブルを事前に構築中。フレーム転送はまだしない |
| ~~Forwarding~~     | ~~○~~      | ~~○~~ | ~~送受信~~ | ~~通常動作~~                                               |

> **STPでは、Blocking・Listening・Learningのいずれか、またはDisabledの場合、フォワーディングではありません。**

---

## 2. RSTP（802.1w）における「フォワーディングでない状態」

RSTPでは状態を3つに集約し、**「Discarding」**という状態がBlocking/Listeningに相当します。

| 状態                 | フレーム転送 | MAC学習 | BPDUの処理  | STP(802.1D)での相当  |
| -------------------- | ------------ | ------- | ----------- | -------------------- |
| **Discarding** | ×           | ×      | 送受信      | Blocking + Listening |
| **Learning**   | ×           | ○      | 送受信      | Learning             |
| ~~Forwarding~~      | ~~○~~      | ~~○~~ | ~~送受信~~ | ~~Forwarding~~      |

> **RSTPでは、DiscardingまたはLearningの場合、フォワーディングではありません。**

---

## 3. 各状態の具体的な意味

### Disabled（無効）

ポートが**管理者によって明示的に無効化**されている状態です。

```
設定例（Cisco）:
interface GigabitEthernet0/1
  shutdown
```

- ケーブルを挿しても、物理層的にダウン
- BPDUも送受信しない
- **意図的な「使っていない」状態**

---

### Blocking / Discarding（ブロッキング / ディスカーディング）

**ループ防止のため、トポロジー上「不要」と判断されたポート**がこの状態になります。

```
【Blockingポートの例】
        [SW-Root]
       /         \
  [SW-A]════════[SW-B]
      ↑_________↑
    このリンクはループになるため、
    SW-B側のポートがBlocking状態
```

- **フレーム転送：しない**（ユーザーデータは一切通らない）
- **MAC学習：しない**
- **BPDU：受信のみ**（STP）または**送受信**（RSTP）

**結果として：**

- そのポートを通じてPCやサーバーは通信できない
- トランクポートがBlockingなら、そのVLANの通信がそのリンクで止まる
- **VRRPの観点では**：そのポートがVRRPを流すべきVLANの唯一の物理ポートなら、SVIがダウンし、VRRP広告も送信できなくなる

---

### Listening / Discarding（リスニング）

ポートが**新しくアクティブになった直後**、または**トポロジー変更が検知された際**に一時的に通る状態です。

- **フレーム転送：しない**
- **MAC学習：しない**
- **BPDU：送受信する**（「誰がルートか」「自分はどの役割か」を協議中）

STPではこの状態で**約15秒（Forward Delay）**待機します。RSTPでは通常この状態に長く留まりません。

> **「通信はまだできないが、トポロジー情報は交換している」段階**

---

### Learning（ラーニング）

トポロジーが安全と判断された後、**MACアドレステーブルを事前に構築する**状態です。

- **フレーム転送：しない**（ユーザーデータはまだ通らない）
- **MAC学習：する**（届いたフレームの送信元MACをテーブルに登録）
- **BPDU：送受信する**

STPではこの状態でも**約15秒（Forward Delay）**待機します。

> **「フレームは転送しないが、どのMACがどのポートにあるかを覚え始める」段階**

**なぜLearningが必要か：**
フォワーディングに移行した瞬間に大量のフレームが届いたとき、**MACテーブルが空だとすべてをフラッディング（全ポートに氾濫）**してしまい、ネットワークが一時的に不安定になるのを防ぐためです。

---

## 4. 状態遷移のイメージ

### STP（802.1D）の場合

```
ポート接続 / no shutdown
     ↓
[Blocking] ──トポロジー確定後──→ [Listening] ──15秒──→ [Learning] ──15秒──→ [Forwarding]
     ↑                                                                    │
     └──────────────── トポロジー変更検知（再計算）──────────────────────────┘
```

**合計で30～50秒かかる**ことがあります。

### RSTP（802.1w）の場合

```
ポート接続
     ↓
[Discarding] ──役割判定（P/A機構）──→ [Learning] ──数秒以内──→ [Forwarding]
     ↑                                                              │
     └──────────── トポロジー変更検知 ────────────────────────────────┘
```

**Edge Portなら即座にForwarding。トランクポートでも数秒以内。**

## 5. 「フォワーディングでない」ことの影響（前後の文脈と接続）

以前の会話で扱った技術との接続で見ると、以下の影響があります。

| 技術・状況                 | フォワーディングでない場合の影響                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------------------- |
| **PC/サーバー接続**  | そのポートに繋がったPCは、IPアドレスを取得できず、一切通信できない                                       |
| **トランクポート**   | そのリンク上の**すべてのVLAN**の通信が止まる                                                       |
| **VRRP環境のL2SW**   | L3SW間のトランクがBlockingなら、VRRP広告が交換できず**デュアルマスター**が発生する可能性           |
| **広域イーサネット** | 事業者網内で冗長リンクがBlockingなら、**予備リンクとして待機**。障害時にForwardingへ移行して冗長化 |
| **OSPF/BGP隣接**     | 隣接ルーター間のL2リンクがBlockingなら、**レイヤー3の隣接関係（adjacency）が成立しない**           |

---

## まとめ

> **フォワーディング状態でない状態には、STP（802.1D）ではDisabled（管理ダウン）、Blocking（ループ防止で塞がれている）、Listening（トポロジー協議中）、Learning（MAC学習中）の4つがあり、RSTP（802.1w）ではDiscarding（Blocking+Listeningに相当）とLearningの2つがあります。いずれも「フレーム転送はしない」という共通点があり、ループ防止やトポロジー安定化のための一時的・恒常的な制限状態です。フォワーディングになると、初めて通常のイーサネット通信が可能になります。**

## なぜIPパケットのままなのか

PCから送信されたデータは、**イーサネットフレーム（L2）の中にIPパケット（L3）がカプセル化された形**でネットワークを流れます。

```
【PCからデフォルトゲートウェイまで】
[イーサネットフレーム]
| 宛先MAC: DGのMAC | 送信元MAC: PCのMAC | タイプ: 0x0800 | [IPパケット] | FCS |
                                                  ↑
                                           宛先IP: インターネット側
                                           送信元IP: PCのIP
```

デフォルトゲートウェイ（L3SWやルーター）は、このフレームを受信すると、**イーサネットヘッダ（MACアドレス部分）を剥がし、中身のIPパケットを取り出します。**

---

## デフォルトゲートウェイ→FWの間でもIPパケット

DGはIPパケットの**宛先IPアドレス**を見て、「次はFWに送る」と判断し、**新しいイーサネットフレーム**にそのIPパケットを包んでFWへ送出します。

```
【DG→FWの間】
[新しいイーサネットフレーム]
| 宛先MAC: FWのMAC | 送信元MAC: DGのMAC | タイプ: 0x0800 | [IPパケット] | FCS |
                                                  ↑
                                           中身のIPパケットはそのまま！
                                           （NATがない場合）
```

**L2ヘッダ（MACアドレス）はホップごとに書き換えられますが、L3のIPパケットはそのままFWに届きます。**

---

## FWはIPパケットを見て動作する

ファイアウォールは基本的に**L3（IPアドレス）・L4（ポート番号）・L7（アプリケーション層）**で動作します。

| FWの確認項目 | 内容 |
|-------------|------|
| **送信元IP** | どの内部PCから来たか |
| **宛先IP** | どの外部サーバーへ向かうか |
| **プロトコル番号** | TCP(6) / UDP(17) / ICMP(1) など |
| **送信元/宛先ポート** | TCP/UDPの場合、どのサービスか（80, 443, 25など） |
| **状態テーブル** | この通信は既存のセッションか、新規か |

FWが許可判断をした後、**再び新しいイーサネットフレームにIPパケットを包んで**、次のホップ（ISPルーターなど）に送出します。

---

## 以前の文脈との接続

### OSPFの観点

DGとFWの間でOSPFが動作している場合、**OSPFはIPパケットの「どのネクストホップへ送るか」を決定**します。FWへの経路がOSPFで学習されていれば、DGは「このIPパケットはFWのIPアドレスへ向ける」と判断します。

### NATの観点

FWで**NAPT（IPマスカレード）**を行う場合、FWを通過する際に**IPヘッダの送信元IPアドレスが書き換えられます**（例：プライベートIP→グローバルIP）。しかし、それでも**「IPパケット」であることに変わりはありません**。L2ヘッダが書き換わるのと同様に、L3ヘッダの一部が書き換わるだけです。

### トランク/VLANの観点

もしDG→FW間が**トランクポート**で、管理VLANや別のVLANが混在している場合でも、**IPパケットが乗るイーサネットフレームにVLANタグが付くだけ**です。中身のIPパケット自体は変わりません。

---

## まとめ

> **デフォルトゲートウェイを通過した後、FWに到達するパケットはIPパケットです。L3デバイス（DG）はイーサネットフレームからIPパケットを取り出し、宛先IPを見て次のホップ（FW）への転送を決定します。次のホップへ送る際は新しいイーサネットフレームに再カプセル化されますが、中身のIPパケットは基本的にそのまま保持されます。FWはこのIPパケットの送信元/宛先IPやポート番号などを確認してフィルタリング判断を行います。**

画像の「表2 G社のネットワーク機器に設定する静的経路情報（抜粋）」において、FW（FW1, FW2）の宛先ネットワークアドレスが複数登録されている理由は、**社内LAN（L3SW側）の配下に複数の異なるサブネット（ネットワークセグメント）が存在しているから**です。

## 1. 複数の宛先アドレス（172.17.11.0 〜 103.0）の意味

FW1・FW2のルーティングテーブルには、以下の4つの社内ネットワーク宛ての経路が個別に登録されています。

* `172.17.11.0/24`

* `172.17.101.0/24`

* `172.17.102.0/24`

* `172.17.103.0/24`


社内ネットワークは用途（例えば、サーバー用、社内PC用、ゲストWi-Fi用など）ごとにVLAN（サブネット）が分けられています。

FW（ファイアウォール）は外部（インターネット等）と内部（社内LAN）の境界に位置するため、**「社内の各サブネット宛ての通信は、すべて社内側のコアスイッチ（L3SW1, L3SW2の仮想IP `172.17.10.4`）へ転送する」** という指示をサブネットごとに設定しているわけです。

## 2. ネクストホップがすべて同じ理由

表を見ると、これら4つの宛先へのネクストホップ（次にデータを送る先）はすべて `172.17.10.4`（L3SW1とL3SW2が共有する仮想IP）となっています。

FWから見ると、宛先のサブネットが `11.0` であっても `101.0` であっても、出口（ネクストホップ）は同じL3SWです。通信を受けたL3SW側が、それぞれのサブネットへ最終的なルーティングを行います。

## 3. 最下行の `0.0.0.0`（デフォルトルート）との違い

FWの最下行にある `0.0.0.0` （サブネットマスク `0.0.0.0`）は**デフォルトルート**と呼ばれます。

* **`172.17.X.X`（具体的に書かれた4つ）:** 「社内宛て」の通信 $\rightarrow$ **L3SWへ転送**

* **`0.0.0.0`（上記以外のすべて）:** 「インターネット（外部）宛て」の通信 $\rightarrow$ **ルータ1（`199.α.β.1`）へ転送**


このように、FWが「社内宛ての通信」と「インターネット宛ての通信」を正しい方向に振り分けるために、社内にあるサブネットのアドレスを個別に指定してルーティング情報を設定しています。
