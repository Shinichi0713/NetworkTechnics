

## TCPとは

TCP（Transmission Control Protocol）とは、インターネット上でデータを「確実に」「順番通りに」届けるための約束事（プロトコル）です。

### 1. 基本的な概念

TCPは、送信者と受信者がお互いの状態を確認しながらデータを送り合うことで、**「届かなかったら届くまで再送する」** という仕組みを持っています。だから、Webページの表示やファイルのダウンロードなど、「欠けや順番の入れ替わりが許されない」通信に使われます。

### 2. 直感的な例え：宅配便の配達

TCPを宅配便に例えるとこうなります。

- **宛名と送り状がある**：どこからどこへ届けるかが明確
- **配達証明がある**：受け取ったら「受け取りました」と返事をする
- **順番に届ける**：箱に「1番」「2番」と書いておき、順番が乱れていたら元通りに並べる
- **紛失したら再送**：「2番が来ていません」と伝えたら、再度送ってくれる

このように、TCPは「確実・順序正確」を重視します。

### 3. 仕組み：どうやって確実に届けるのか

TCPには、以下のような重要な仕組みがあります。

__① 3ウェイ・ハンドシェイク（接続の確立）__

通信を始める前に、送受信者が3回やり取りをして「準備OKです」と確認します。
1. 「通信していいですか？」（SYN）
2. 「いいですよ、こちらも準備OKです」（SYN-ACK）
3. 「では、始めます」（ACK）

__② シーケンス番号と確認応答（ACK）__

送るデータに「1番から1000バイト目」といった番号（シーケンス番号）を付けます。受信者は「1000バイト目まで受け取りました」（ACK）と返します。これで「確実に届いたか」が分かります。

__③ 再送制御__

一定時間内にACKが返ってこなければ、「届いていない」と判断して同じデータを再度送ります。

__④ フロー制御（受信側の処理能力に合わせる）__

受信者が「今はこれ以上受け取れません」と伝え、送信者はその量を調整します。これで受信者がパンクするのを防ぎます。

__⑤ 輻輳制御（ネットワークの混雑に合わせる）__

ネットワークが混雑していれば、送信速度を落とします。道路の渋滞を避けるように、通信量を調整します。


### 4. 境界：UDPとの違い

TCPは「確実・順序重視」ですが、必ずしもすべての通信に最適とは限りません。UDP（User Datagram Protocol）という別のプロトコルと比べると、違いが明確です。

| 特徴 | TCP | UDP |
|------|-----|-----|
| 接続の確立 | ある（3ウェイ・ハンドシェイク） | ない |
| 信頼性 | 高い（再送・順序制御あり） | 低い（ベストエフォート） |
| 順序保証 | ある | ない |
| 速度 | やや遅い（制御のオーバーヘッド） | 速い |
| 用途 | Web（HTTP/HTTPS）、メール、ファイル転送 | 動画配信、DNS、オンラインゲーム |

動画配信やオンラインゲームなど、「少しの欠落は許容できるけど、遅延は許容できない」場合はUDPが使われることもあります。

## 通信の手続き

TCPの通信は、主に**3つの段階**で進みます。

1. **接続を確立する**（3ウェイ・ハンドシェイク）
2. **データを送り合う**（実際の通信）
3. **接続を終了する**（4ウェイ・ハンドシェイク）

それぞれを具体的に見ていきましょう。

### 1. 接続の確立：3ウェイ・ハンドシェイク

TCPでは、データを送る前に「お互いの準備ができているか」を確認します。これを**3ウェイ・ハンドシェイク**と呼びます。

__例え：電話をかけるとき__

1. **あなた** → 「もしもし、田中です」（相手に話しかける）
2. **田中さん** → 「はい、田中です。どうぞ」（受け取った＆こちらも準備OK）
3. **あなた** → 「実は…」（本題を始める）

__TCPの実際のやり取り__

| ステップ | 送信者 | 内容 | フラグ |
|---------|--------|------|--------|
| ① | クライアント → サーバー | 「通信を始めたいです」 | SYN |
| ② | サーバー → クライアント | 「OKです。こちらも準備できました」 | SYN + ACK |
| ③ | クライアント → サーバー | 「では、始めます」 | ACK |

- **SYN**（Synchronize）：同期要求。通信を始めたい合図。
- **ACK**（Acknowledgment）：確認応答。相手の要求を受け取った合図。

これで「両方とも送受信の準備ができた」ことが確認でき、通信が始まります。

### 2. データ転送：確実に・順番通りに届ける

接続が確立したら、実際にデータを送ります。TCPがここで行う主な仕事は4つです。

__① シーケンス番号で「順番」を管理する__

データは小さな塊（セグメント）に分けて送られます。各セグメントには**シーケンス番号**という「通し番号」が付きます。

```
送信データ：「ABCDEFGHIJ」（10バイト）

セグメント1：ABC（シーケンス番号：1）
セグメント2：DEF（シーケンス番号：4）
セグメント3：GHI（シーケンス番号：7）
セグメント4：J（シーケンス番号：10）
```

受信者はこの番号を見て、順番が入れ替わっていても元通りに並べ直せます。

__② ACKで「届いたか」を確認する__

受信者はデータを受け取るたびに、**次に欲しいデータの番号**を伝えます。これが**ACK（確認応答）**です。

```
サーバー → クライアント：「ABC」を送信（シーケンス番号：1）
クライアント → サーバー：「4番まで届きました。次は4番をください」（ACK = 4）
サーバー → クライアント：「DEF」を送信（シーケンス番号：4）
クライアント → サーバー：「7番まで届きました。次は7番をください」（ACK = 7）
```

__③ 再送制御：届かなければ送り直す__

サーバーはデータを送ったら、一定時間内にACKが返ってくるのを待ちます。もし時間切れになってもACKが来なければ、「途中で消えたか、届いていない」と判断して**同じデータを再度送信**します。

```
サーバー → クライアント：「GHI」を送信
（ACKが5秒待っても来ない…）
サーバー → クライアント：「GHI」を再度送信
クライアント → サーバー：「10番まで届きました」（ACK = 10）← 今度は届いた！
```

__④ ウィンドウ制御：一度に送る量を調整する__

ACKを1回送るごとに次のデータを送るのでは効率が悪いので、TCPは **「一度に複数のセグメントを送って、まとめてACKを待つ」** 仕組みを持っています。これを**スライディングウィンドウ**と呼びます。

```
サーバー：「ABC」「DEF」「GHI」をまとめて送信（ウィンドウサイズ：3）
クライアント：「10番まで届きました」（ACK = 10）← まとめて1回のACK
```

受信者の処理能力やネットワークの混雑具合に応じて、このウィンドウサイズを動的に調整します。これが**フロー制御**（受信側に合わせる）と**輻輳制御**（ネットワークに合わせる）です。

### 3. 接続の終了：4ウェイ・ハンドシェイク

通信が終わったら、きちんと「おしまい」と伝えて接続を閉じます。これには**4回**のやり取りが必要です。

__例え：電話を切るとき__

1. **あなた** → 「では、失礼します」（もう話すことはない）
2. **田中さん** → 「はい、分かりました」（了解）
3. **田中さん** → 「こちらこそ、失礼します」（こちらも終わりです）
4. **あなた** → 「はい、失礼しました」（了解）

__TCPの実際のやり取り__

| ステップ | 送信者 | 内容 | フラグ |
|---------|--------|------|--------|
| ① | クライアント → サーバー | 「もう送るものはありません」 | FIN |
| ② | サーバー → クライアント | 「分かりました」 | ACK |
| ③ | サーバー → クライアント | 「こちらも送るものはありません」 | FIN |
| ④ | クライアント → サーバー | 「分かりました」 | ACK |

- **FIN**（Finish）：終了要求。もうデータを送らない合図。

これで、両方向の通信がきちんと終了し、リソースが解放されます。

## 開発経緯

TCPの開発経緯は、現在のインターネットそのものの誕生と深く関わっています。以下、歴史的な流れを追って説明します。

### 1. 背景：ARPANETの誕生と限界

1969年、米国防総省のARPA（Advanced Research Projects Agency）の資金提供で、世界初のパケット通信ネットワークである**ARPANET**が構築されました。
当初は数台のコンピュータをつなぐだけの小さなネットワークでしたが、1970年代初頭には電子メールなどの利用が急増し、ネットワークの重要性が急速に高まりました。

しかし、ARPANETには大きな課題がありました。

- **異なるネットワーク同士をつなげられない**：ARPANETは一つのネットワークとして機能していましたが、衛星通信網や無線ネットワークなど、異なる技術を使うネットワークとは直接通信できませんでした。
- **信頼性が低い**：パケットが途中で失われたり、順番が入れ替わったりしても、アプリケーション側で対処しなければなりませんでした。

### 2. 開発者：Vint CerfとBob Kahn

この課題を解決するため、当時ARPAで働いていた**ボブ・カーン（Bob Kahn）** と、スタンフォード大学にいた**ヴィント・サーフ（Vint Cerf）** が協力して新しいプロトコルの設計を始めました。
彼らの目標は、**「仕組みの異なるネットワーク同士を、ひとつのインターネットとして動かすこと」** でした。これは当時としては画期的な発想でした。

__例：異なる言語を話す国同士の通訳__

ARPANET、衛星ネットワーク、無線ネットワークは、それぞれ「異なる言語」を話していました。CerfとKahnが作ったのは、これらすべてのネットワークが共通して使える「通訳＝共通言語」でした。それがTCP/IPです。


### 3. 1974年：TCPの誕生

1973年に設計をまとめ、**1974年5月**にCerfとKahnは論文「A Protocol for Packet Network Intercommunication」を発表し、TCPの概念を世界に示しました。
当初、TCPは現在の「TCP」と「IP」の役割を**ひとつのプロトコル**で担っていました。つまり、

- パケットの配送（現在のIPの役割）
- 信頼性のある通信（現在のTCPの役割）

をすべてTCPがやっていたのです。後に、この機能が分離されて「TCP」と「IP」という2つのプロトコルになりました。

### 4. 1983年：ARPANETのTCP/IP移行（フラグ・デー）

TCP/IPはすぐに普及したわけではありませんでした。ARPANETは長らく従来のプロトコル（NCP：Network Control Program）を使い続けていました。

そして、**1983年1月1日**、ARPANETは正式にNCPからTCP/IPへ移行しました。この日は **「フラグ・デー（Flag Day）」** と呼ばれ、今日のインターネットの基盤が整った象徴的な日となりました。

### 5. なぜTCPが必要だったのか

CerfとKahnがTCPを設計した根本的な動機は、以下の2つでした。

| 課題 | TCPによる解決 |
|------|--------------|
| 異なるネットワーク間の通信ができない | 共通のプロトコルで「インターネット」を実現 |
| パケットの紛失・順番の乱れに対処できない | シーケンス番号・ACK・再送制御で信頼性を保証 |
| アプリケーションが通信の詳細を意識しすぎる | TCPが通信の複雑さを肩代わりし、開発者を解放 |

つまり、TCPは「ネットワークの複雑さを隠して、アプリケーションが簡単に通信できるようにする」ための層として設計されたのです。

## 近年の研究

TCPに代わるプロトコルとして、近年最も注目されているのは**QUIC（Quick UDP Internet Connections）** です。HTTP/3の基盤として、GoogleやCloudflareなどで既に広く使われています。

### 1. QUICとは何か

QUICは、**UDPの上に「信頼性のある通信」を再構築した**プロトコルです。TCPがOSのカーネルで動くのに対し、QUICはアプリケーション層（ユーザースペース）で動作し、より柔軟に設計されています。

__直感的な例え：高速道路の車線__

TCPは「1本の道路に1台ずつしか走れない」ようなもので、先頭の車が止まると後続もすべて止まります。QUICは「同じ道路に複数の車線があり、ある車線が渋滞しても他の車線は走り続けられる」ような仕組みです。

### 2. TCPではダメだった3つの理由

__① ヘッドオブラインブロッキング（先頭の詰まり）__

TCPは「順番通りに届ける」ことを徹底します。しかしHTTP/2で1本のTCP接続に複数のリクエストを並列化（多重化）しても、TCPレベルで1つのパケットが失われると、その後のすべてのリクエストが待たされるのです。

```
【TCPの場合】
リクエストA（画像） ──►
リクエストB（CSS）  ──►
リクエストC（JS）   ──►
        ↓
パケット1つ失われる → すべてのリクエストが待たされる！

【QUICの場合】
ストリームA（画像） ──►  パケット失われてもAだけ再送
ストリームB（CSS）  ──►  Bはそのまま進行
ストリームC（JS）   ──►  Cもそのまま進行
```

QUICでは、各ストリームが独立して動作するため、あるストリームのパケットロスが他のストリームに影響しません。

__② 接続確立が遅い__

TCPでは通信前に3ウェイ・ハンドシェイク（1.5RTT）が必要で、TLS暗号化を加えるとさらに2RTTかかり、合計で3〜4往復が必要でした。

QUICでは、接続確立と暗号化のハンドシェイクを**同時に行い**、初回接続でも**1RTT**、以前接続したことがあれば**0RTT**で通信を開始できます。

| プロトコル | 接続確立にかかる往復回数 |
|-----------|----------------------|
| TCP + TLS 1.2 | 3〜4 RTT |
| TCP + TLS 1.3 | 2 RTT |
| QUIC（初回） | 1 RTT |
| QUIC（再開時） | 0 RTT |

__③ モバイル環境での接続切れ__

TCPは「送信元IPアドレス＋ポート番号」で接続を識別します。スマートフォンがWi-Fiから4G/5Gに切り替わるとIPアドレスが変わり、**接続が切れてしまいます**。

QUICは**Connection ID**という固有の識別子を使うため、IPアドレスが変わっても接続を維持できます。

### 3. QUICの用途

| 用途 | 理由 |
|------|------|
| **Webサイト表示（HTTP/3）** | ページ読み込み速度の向上 |
| **動画ストリーミング** | 途切れにくい、スムーズな再生 |
| **オンラインゲーム** | 低遅延、接続切れに強い |
| **リアルタイム通信（WebRTCなど）** | 高速な接続確立 |

Google、YouTube、Facebook、Cloudflareなど、主要なWebサービスの多くが既にQUICに対応しています。

### 4. TCPとQUICの比較

| 項目 | TCP | QUIC |
|------|-----|------|
| 基盤プロトコル | IP直接 | UDP上 |
| 接続確立 | 3ウェイ・ハンドシェイク＋TLS別途 | 統合ハンドシェイク（1RTT/0RTT） |
| ストリーム多重化 | あり（HTTP/2）だがTCPレベルで依存 | 独立したストリーム（HoLブロッキングなし） |
| IP変更時の接続維持 | 不可 | 可能（Connection ID） |
| 暗号化 | オプション（TLS別途） | 必須（TLS 1.3相当が組み込み） |
| 実装場所 | OSカーネル | アプリケーション層（ユーザースペース） |

### 5. なぜTCPを改良せず、UDPを選んだのか

TCPはOSカーネルの中に深く組み込まれており、世界中のルーターやOSに変更を加えるのは現実的ではありません。UDPは非常にシンプルなプロトコルなので、その上に新しい仕組みを自由に構築でき、既存のインフラに影響を与えずに導入できるのです。

## 総括

TCPはインターネットでデータを「確実に、順番通りに」届けるための基本プロトコルです。以下、その全体像を簡潔にまとめます。

### 1. TCPの核心

TCPは送信者と受信者が互いの状態を確認しながら通信し、**パケットが失われれば再送し、順番が乱れれば並べ直す**ことで、信頼性の高いデータ転送を実現します。Webページの表示やファイル転送など、欠けや順序の狂いが許されない通信に使われます。

### 2. 通信の3段階

| 段階 | 内容 |
|------|------|
| **接続確立** | **3ウェイ・ハンドシェイク**（SYN → SYN+ACK → ACK）で双方の準備を確認 |
| **データ転送** | シーケンス番号で順序管理、ACKで到着確認、タイムアウトで再送、ウィンドウ制御で流量調整 |
| **接続終了** | **4ウェイ・ハンドシェイク**（FIN → ACK → FIN → ACK）で双方の送信完了を確認して切断 |


### 3. 開発の歴史

- **1969年**：米国防総省のARPAがARPANETを構築。しかし異なるネットワーク間の接続や信頼性に課題が残る。
- **1974年**：**Vint Cerf**と**Bob Kahn**が論文を発表し、異なるネットワークを統合するTCPの概念を提示。当初はIPの役割も兼ねていた。
- **1983年**：ARPANETが従来のNCPからTCP/IPへ全面移行（**フラグ・デー**）。これが現在のインターネットの基盤となる。

### 4. TCPの限界とQUICの登場

現代のWeb通信ではTCPの以下の課題が浮上しました。

1. **ヘッドオブラインブロッキング**：TCP上で多重化しても、1パケットのロスで後続すべてが待たされる。
2. **接続確立の遅さ**：TCPの3ウェイとTLSのハンドシェイクが別々に必要で、複数往復（RTT）がかかる。
3. **モバイル環境での接続切れ**：IPアドレス変更で接続が途切れる。

これを解決するため、**QUIC**（HTTP/3の基盤）が開発されました。UDP上に信頼性制御を再構築し、**0RTT接続・ストリーム単位の独立性・Connection IDによる接続維持**を実現。GoogleやCloudflareなどで既に広く使われています。

| 比較項目 | TCP | QUIC |
|---------|-----|------|
| 基盤 | IP直接 | UDP上 |
| 接続確立 | 3ウェイ＋TLS別途 | 統合ハンドシェイク（1RTT/0RTT） |
| ストリーム | TCPレベルで依存 | 独立（HoLブロッキングなし） |
| IP変更時 | 接続切断 | Connection IDで維持 |
| 暗号化 | オプション | TLS 1.3相当が必須 |

### まとめ

TCPは「確実・順序重視」という強みで半世紀以上にわたりインターネットを支えてきました。しかし、モバイル化と高速化が求められる現代では、その設計上の制約が課題となり、UDP上に再構築された**QUIC/HTTP/3**へと進化しています。TCPが「信頼性の土台」を築き、QUICが「速度と柔軟性」を追加した形と言えるでしょう。
