**Security Association (SA)** とは、IPsec（VPN）通信を行う2台の機器間で結ばれる、**「通信のルールに関する合意（契約）」**のことです。

IPsecでパケットを送る前に、「どの暗号を使うか」「鍵は何にするか」をあらかじめ決めておき、その約束事を管理する「枠組み」だと考えてください。

---

### 1. なぜ「SA」が必要なのか？

インターネットのような公共の場では、誰とでも通信が可能です。しかし、VPNを張る相手とは、**「自分たちだけにしか分からない特別なルール」**で通信をしなければなりません。

パケットを送るたびに「暗号はどうする？」「鍵はこれでいい？」と確認していては通信が遅くなるため、最初に**「このルール（SA）に基づいて通信しよう」**と契約書を交わしておくのです。

---

### 2. SAに含まれる主な「契約内容」

SAには、以下のような情報が記録されています。

* **暗号アルゴリズム:** AES、3DESなど、どの方式で暗号化するか。
* **ハッシュアルゴリズム:** SHA-256など、改ざん検知に何を使うか。
* **暗号鍵:** データの暗号化・復号に使う共通鍵。
* **有効期限（ライフタイム）:** この契約をいつまで有効とするか（時間や通信量）。
* **SPI (Security Parameter Index):** たくさんの契約がある中で、どの契約（SA）を使うかを識別するためのID番号。

---

### 3. SAの重要なルール：片道通行

SAの最も特徴的な点は、**「片道（単方向）で1本」**というルールです。

双方向で通信をするためには、必ず**2本のSA**が必要になります。

* **SA（上り）:** 拠点Aから拠点Bへ送るためのルール。
* **SA（下り）:** 拠点Bから拠点Bへ送るためのルール。

---

### 4. SAはどうやって作られる？（IKEの役割）

このSAを自動で作り、鍵を交換してくれるプロトコルが **IKE (Internet Key Exchange)** です。IKEは2段階でSAを作ります。

* **ISAKMP SA (Phase 1):** まずは「安全に相談するためのトンネル」を作ります。これ自体は管理用のSAです。
* **IPsec SA (Phase 2):** Phase 1で作った安全なトンネルの中で、実際にデータを運ぶための「本番用SA」を作ります。

---

### まとめ

Security Association (SA) は、**「暗号通信を行うためのセットアップ済みの契約書」**です。

ルーターはこのSA（契約書）をメモリに保存しておき、パケットが来たら「SPI（契約番号）」を見て、瞬時に暗号化や復号の処理を行います。

**次は、このSAが何らかの理由で切れてしまった時に起こるトラブルや、再接続の仕組み（DPD：Dead Peer Detection）についてお話ししましょうか？**


EAPは現在も、**企業ネットワーク・モバイル通信・クラウド環境**などで広く使われています。以下に主な利用場面と、その理由をまとめます。

## 現在の主な利用場面

### 1. 企業・学校のWi-Fi認証（WPA2-Enterprise / WPA3-Enterprise）

最も一般的な利用場面です。家庭用Wi-Fiのように「共通のパスワード（PSK）」を使うのではなく、**ユーザーごとに異なる認証情報**で接続します。[Enterprise Wi-Fi Authentication: EAP Methods Guide 2026](https://fleetdm.com/articles/enterprise-wifi-authentication-methods)

- **使われる方式**：[EAP-TLS](https://sageaxe.com/blog/802-1x-eap-tls-certificate-authentication)（証明書）、[PEAP](https://www.purple.ai/en-us/guides/eap-tls-vs-peap-which-authentication-protocol-is-right-for-your-network)（ID/パスワード）、[EAP-TTLS](https://www.ironwifi.com/blogs/best-eap-methods-wifi/) など
- **WPA3-Enterprise 192-bitモード**では、**EAP-TLSのみが許可**されるようになりました（セキュリティ要件の厳格化）。[What Are the EAP Method Requirements For WPA3-Enterprise?](https://securew2.com/blog/eap-method-requirements-for-wpa3-enterprise)

### 2. 有線LANのポート認証（IEEE 802.1X NAC）

無線だけでなく、**オフィスのLANポート**にケーブルを挿した際の認証にも使われます。認証に失敗した端末はスイッチポートで遮断されるため、不正端末の侵入を防ぎます。[802.1X Network Access Control Enterprise Deployment](https://www.decryptiondigest.com/blog/network-access-control-8021x-deployment)

### 3. VPN接続の認証

リモートワークなどで、社外からVPN（SSL-VPNやIPsec）に接続する際のユーザー認証フレームワークとしても使われます。[Windows におけるネットワーク アクセスの拡張認証プロトコル (EAP)](https://learn.microsoft.com/ja-jp/windows-server/networking/technologies/extensible-authentication-protocol/network-access)

### 4. 5G / モバイルネットワークの認証

比較的新しい利用場面として、**5Gネットワーク**でもEAPが使われています。具体的には [EAP-AKA'](https://www.rfc-editor.org/rfc/rfc9048.html)（Authentication and Key Agreement prime）という方式で、SIM/eSIMを使った端末認証に使用されます。[EAP AKA Prime Explained](https://www.p1sec.com/blog/eap-aka-prime-what-aka-changes-and-why-it-matters-in-mobile-network-security)

また、**Wi-Fiと5Gの統合**（企業Wi-Fiを5Gコアネットワークに接続する場面）でも、EAPを使ったSIMベース認証の研究・運用が進んでいます。[EAP and Seamless Access with SIM Authentication](https://syndicated.wifinowglobal.com/resource/eap-and-seamless-access-with-sim-based-authentication/)

## なぜEAPが使われるのか（利用される理由）

| 理由 | 説明 |
|------|------|
| **① ユーザー・デバイスごとの個別認証ができる** | 共通パスワード（PSK）ではなく、ユーザーIDや証明書で個別に認証・監査できる。退職者のアカウント無効化も即座に可能。 |
| **② 多様な認証方式を統一的に扱える** | パスワード、証明書、SIM、指紋など、要件に応じて認証方式を選べる「共通の枠組み」として機能する。 |
| **③ バックエンド（RADIUS）との連携が標準化されている** | APやスイッチは認証処理を中継するだけで、実際の認証判断を一元管理できる。大規模環境での運用に適している。 |
| **④ 相互認証が可能** | EAP-TLSなどでは、サーバー側も証明書で認証されるため、「偽AP（Evil Twin）」への接続を防げる。 |
| **⑤ フィッシング耐性** | EAP-TLSの証明書ベース認証は、ID/パスワードを使わないためフィッシング攻撃に強い。最新のセキュリティ基準（WPA3-Enterprise 192-bit）でも採用されている。 |
| **⑥ 通信開始前（データリンク層）で認証できる** | IPアドレスの割り当て前に認証を完了できるため、不正端末をネットワークの入口で遮断できる。 |

## まとめ

> **EAPは現在、企業Wi-Fi（WPA2/WPA3-Enterprise）、有線LANの802.1X、VPN、さらには5Gモバイル認証まで、幅広く使われています。使われる理由は、「個別認証・相互認証・バックエンド連携・フィッシング耐性」など、セキュリティ要件の高い環境で求められる機能を、統一的なフレームワークとして提供しているからです。**


「通常のTCPによる接続」との比較ですが、文脈から判断して**EAPによる認証のやり取り**との違いを説明します。

## 結論：動作するレイヤーと目的が根本的に異なる

| 項目 | EAP（認証フレームワーク） | TCP（トランスポート層プロトコル） |
|------|--------------------------|----------------------------------|
| **OSI層** | データリンク層（L2） | トランスポート層（L4） |
| **目的** | **「誰が接続しようとしているか」を確認する** | **「データを確実に届ける」** |
| **必要な前提** | IPアドレス不要 | IPアドレスが必要（L3の上に乗る） |
| **やり取りするもの** | Identity、認証方式のネゴシエーション、証明書、パスワード | シーケンス番号、ACK、ウィンドウサイズ、ポート番号 |
| **接続確立後** | Success/Failureで**認証結果を通知して終了** | アプリケーション間で**継続的なデータ通信**を行う |
| **ポート番号** | 使わない | 使う（HTTP:80、HTTPS:443など） |

## 具体的な違い

### 1. タイミングが異なる：TCPよりも「前」で動作する

通常のTCP接続は、**IPアドレスが割り当てられてから**、アプリケーション（Webブラウザ、メールなど）が通信を始めるために使います。

一方、EAPは**IPアドレスがまだない段階**で動作します。

```
[端末] → EAP認証（IPなし、L2で動作） → 認証成功 → IP割り当て → TCP接続（L4） → アプリ通信
   ↑_________________ ここがEAPの管轄 ___________________________↑
                                                    ↑____ TCPの管轄 ____↑
```

つまり、**EAPはTCP接続の「入口の警備」で、TCPは「入口を通った後の運搬」**です。

---

### 2. TCPは「通信の信頼性」を、EAPは「接続する権利」を扱う

- **TCP**は、一度接続が許可された後に「データが欠けず、順序通りに届くか」を保証します。再送制御、順序制御、輻輳制御などが主な仕事です。
- **EAP**は、「この端末・このユーザーに通信を許可するか」を判断します。許可されなければ、TCP接続を始めることすらできません。

---

### 3. EAPは「接続確立」ではなく「認証フレームワーク」

TCPには「3ウェイハンドシェイク（SYN → SYN-ACK → ACK）」という接続確立の手順がありますが、これは**通信路の確保**です。

EAPにはRequest/Response/Success/Failureというメッセージ交換がありますが、これは**認証情報のやり取り**であり、通信路そのものを確保するものではありません。EAPが成功した後、初めてネットワークアクセスが許可されるのです。

---

## もし「ポートフォワーディングされたTCP接続」との比較なら

もし質問が「ポートフォワーディングされた接続」と「通常のTCP接続」の違いという意味でしたら、以下のようになります。

| 項目 | 通常のTCP接続 | ポートフォワーディングされたTCP接続 |
|------|-------------|----------------------------------|
| **宛先IP** | 通信相手の実IP | NATのグローバルIP（実際は内部に転送される） |
| **ポート番号** | 実際のサービスポート | 外部用と内部用で異なる場合がある（8080→80） |
| **通信相手の認識** | 直接相手と通信している | ルーター/FWを介在して、中継されている |
| **セキュリティ** | 通常 | NAT越しのため、接続元の制御が必要 |

---

## まとめ

> **EAPとTCPは「全く別のレイヤーで別の目的」を持っています。EAPはデータリンク層で「接続する権利」を確認する認証フレームワークであり、TCPはトランスポート層で「許可された後のデータ通信」を確実に届けるプロトコルです。EAPはTCPよりも前の段階で動作し、IPアドレスすら不要な状態で認証を完了させます。**



EAPは、**IPアドレスではなく、データリンク層（レイヤー2）の仕組み**でクライアントを識別・通信しています。

---

## IPアドレスが不要な理由

EAPはデータリンク層（L2）で動作するため、**IP（レイヤー3）が存在する前提では動作しません**。代わりに、以下の方法でクライアントを識別・通信しています。

---

## クライアントを識別する3つの仕組み

### 1. 物理的な接続ポート（IEEE 802.1Xの場合）

有線LAN（IEEE 802.1X）では、**スイッチの「どの物理ポートに何が接続されているか」**で識別します。

```
[PC-A]──[スイッチ Port 3]  ← 「Port 3に接続された端末」と認識
[PC-B]──[スイッチ Port 7]  ← 「Port 7に接続された端末」と認識
```

スイッチは各ポートごとに**認証状態（未認証/認証済み）**を管理しています。認証前はそのポートの通信を遮断し、認証成功後に開放します。これが「ポートベースのネットワークアクセス制御」と呼ばれる理由です。

無線LAN（WPA2/WPA3-Enterprise）の場合は、**APとの「Association（関連付け）」という論理的な接続単位**で識別します。各無線クライアントは固有のAssociation IDを持ち、APはそれぞれ別々のEAPセッションを管理します。

### 2. MACアドレス（データリンク層アドレス）

イーサネットフレームには**送信元MACアドレス**と**宛先MACアドレス**が含まれています。EAPメッセージ（EAPOLフレーム）もこのイーサネットフレームに乗って運ばれます。

```
イーサネットフレームの構造:
┌─────────────┬─────────────┬──────────┬────────────────┐
│ 宛先MAC      │ 送信元MAC    │ タイプ    │ ペイロード(EAPOL)│
│ (例: APのMAC)│ (例: PCのMAC)│ 0x888E   │ (EAPメッセージ) │
└─────────────┴─────────────┴──────────┴────────────────┘
```

スイッチやAPは、この**送信元MACアドレス**を見て「どの端末からのEAPメッセージか」を判断します。

### 3. EAP-Response/Identity（論理的な識別子）

EAPの認証シーケンスの最初に、認証者から**EAP-Request/Identity**が送信され、クライアントは**EAP-Response/Identity**で自身の識別子（通常はユーザー名）を返します。

```
認証者 → クライアント: EAP-Request/Identity
クライアント → 認証者: EAP-Response/Identity ("tanaka@example.com")
```

この識別子を使って、RADIUSサーバーは「誰が認証しようとしているか」を判断し、適切な認証処理（パスワード照合や証明書検証）を行います。

---

## 通信の流れ（IPなしでどうやり取りするか）

### IEEE 802.1X + EAPOL の場合

EAPメッセージは**EAPOL（EAP over LAN）**という専用のフレームにカプセル化され、イーサネットフレームで直接運ばれます。

```
[PC] ──EAPOLフレーム──→ [スイッチ] ──RADIUSパケット(EAP中継)──→ [RADIUSサーバー]
  ↑                                                      ↑
MACアドレスで識別                                    EAPメッセージを
                                                    そのまま中継
```

- **PCとスイッチ間**：EAPOLフレーム（イーサネット上の特別なフレーム、タイプ `0x888E`）
- **スイッチとRADIUSサーバー間**：RADIUSパケットの中にEAPメッセージをそのまま封入（[RFC 3579](https://tex2e.github.io/rfc-translater/html/rfc3579.html)）

どちらも**IPアドレスを使いません**。PCとスイッチ間はL2フレーム、スイッチとRADIUS間はUDPベースのRADIUSですが、RADIUSサーバーにはIPが設定されています（スイッチ自身はIPを持ってRADIUSサーバーと通信します）。

### PPPの場合

ダイヤルアップやVPN（L2TPなど）では、**PPPフレーム**の中にEAPメッセージが直接載ります。PPPはポイントツーポイントの接続なので、「線の向こう側にいる相手」としか接続していません。相手を識別する必要がない（物理的に1対1）ため、IPアドレスは不要です。

## まとめ

> **EAPはIPアドレスを使わず、データリンク層の仕組みでクライアントを識別します。有線では「物理ポート＋MACアドレス」、無線では「APとのAssociation（論理接続）＋MACアドレス」で識別し、EAP-Response/Identityで「誰が認証しようとしているか（ユーザー名など）」を論理的に伝えます。IPアドレスは認証が成功してから初めて割り当てられるため、EAPの動作には一切不要です。**

VPNとPPPの関係は、**「PPPはVPNの構築に使われることがある下位層プロトコル」**というものです。ただし、**「VPN = PPP」ではなく、「一部のVPN技術がPPPを中核として使う」**という関係です。

## 1. PPPとは（再確認）

[PPP](https://ja.wikipedia.org/wiki/Point-to-Point_Protocol)（Point-to-Point Protocol）は、**2点間（ポイントツーポイント）の直接接続で、データリンク層の通信と認証を行うプロトコル**です。

- 元々はダイヤルアップ接続（電話回線＋モデム）のために設計されました
- [EAP](https://ja.wikipedia.org/wiki/Extensible_Authentication_Protocol)を使ったユーザー認証が可能
- IPアドレスの割り当て（ネゴシエーション）も行える

---

## 2. VPNとは

[VPN](https://ja.wikipedia.org/wiki/%E3%83%90%E3%83%BC%E3%83%81%E3%83%A3%E3%83%AB%E7%A7%81%E6%9C%89%E7%B6%B2%E8%B7%AF)（Virtual Private Network）は、**インターネットなどの公共ネットワーク上に「仮想的な専用回線」を作る技術**です。通信内容を暗号化・カプセル化し、遠隔地同士をあたかも同じLANにいるように接続します。

---

## 3. PPPとVPNの関係

### 関係の本質：**「PPPフレームをインターネット上でトンネリングする」**

一部のVPN技術（特にL2TP系）は、**PPPで確立されたセッションを「中身」として、それをIPネットワーク上でトンネリング**します。

```
[リモートPC]──(PPPセッション: 認証・IP割り当て)──┐
                                                  │
                                            [L2TPトンネル]
                                        （PPPフレームをUDP/IPでカプセル化）
                                                  │
                                           [VPNサーバー/LNS]
                                                  │
                                           [社内ネットワーク]
```

### 具体的な組み合わせ：L2TP/IPsec

最も代表的な「PPPを使うVPN」が **[L2TP](https://ja.wikipedia.org/wiki/Layer_2_Tunneling_Protocol)/IPsec** です。

1. **PPP**：クライアントとVPNサーバー間で、ユーザー認証（EAPやMS-CHAPなど）とIPアドレス割り当てを行う
2. **L2TP**：PPPフレームをUDPパケットに乗せてトンネリングする（PPPの「運搬手段」）
3. **IPsec**：通信全体を暗号化・完全性保護する（PPPの「保護手段」）

つまり、**PPPが「認証と設定」の役割**、**L2TPが「トンネリング」の役割**、**IPsecが「暗号化」の役割**を担い、3つが組み合わさってVPNが成立します。

---

## 4. PPPを使うVPNと使わないVPN

| VPN技術 | PPPを使うか | 説明 |
|--------|------------|------|
| **L2TP/IPsec** | ◎ 使う | PPPフレームをL2TPでトンネリング。Windows/macOS/iOS/Android標準対応。 |
| **PPTP** | ◎ 使う | PPPフレームをGREでトンネリング。古い技術で現在は非推奨（暗号化が弱い）。 |
| **SSTP** | ◎ 使う | Microsoft製。PPPトラフィックをHTTPS（SSL/TLS）で運ぶ。 |
| **SSL-VPN / TLS-VPN** | ✕ 使わない | OpenVPN、FortiClientなど。PPPではなく独自のTLSベースプロトコルで認証・暗号化。 |
| **IPsec VPN（IKEv2）** | ✕ 使わない | IKEv2で認証と鍵交換を行い、IPsecで暗号化。PPPは関与しない。 |
| **WireGuard** | ✕ 使わない | 最新のVPNプロトコル。PPPを使わず、極めて軽量な独自プロトコル。 |

## 5. なぜPPPがVPNに使われるのか

PPPがVPN（特にL2TP系）に採用される理由は、以下の機能がVPNに必要なものと重なるからです。

| PPPの機能 | VPNで必要な理由 |
|----------|----------------|
| **ユーザー認証** | リモートユーザーが正当か確認する（EAP/CHAP/MS-CHAPなど） |
| **IPアドレスの動的割り当て** | 接続ごとにVPNクライアントに社内IPを割り当てる |
| **複数プロトコルの多重化** | IPだけでなく、必要に応じて他のプロトコルも運べる |
| **リンク品質の監視** | 接続状態の監視と管理 |

---

## まとめ

> **VPNとPPPの関係は、「PPPがVPNの認証・設定の土台として使われることがある」というものです。特にL2TP/IPsecやSSTPなどのVPNでは、PPPがユーザー認証とIP割り当てを担当し、L2TPやSSL/TLSがそのPPPフレームをインターネット上で運ぶ役割を担います。ただし、現代のSSL-VPNやWireGuard、IKEv2/IPsecなどではPPPを使わない実装も多く、「VPNに必ずPPPが必要」というわけではありません。**
