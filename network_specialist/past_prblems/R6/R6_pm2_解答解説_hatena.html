問1 データセンターのネットワークの検討（VXLAN／EVPN）

1.1 出題の狙い

出題趣旨は、データセンター事業者や通信事業者のような大規模ネットワークでは、拡張性やマルチテナント対応が重要であり、その解決策としてVXLANとEVPNが使われる、というものです。VXLANで構成したL2オーバーレイにEVPNを適用する事例を通して、L2／L3の基礎技術の理解を問うています。

特に問われたのは次の4点です。

  1. VXLANのカプセル化の構造（VNI、UDP、VTEP）
  2. アンダーレイのOSPF（LSDB、SPF、ECMP、ルータID、ループバック）
  3. VXLANのデータプレーン学習とBUMフレームのマルチキャスト転送
  4. EVPNのコントロールプレーン（MP-BGP、ルートリフレクタ、ESI）による変化

1.2 前提知識の整理

VXLANパケットの構造

VXLANは「L2フレームをL3ネットワークでトンネリングする」技術です。元のイーサネットフレームをそのまま内側に持ち、外側に次のヘッダーを付けます。

+----------------+----------+--------------+---------------------------+
| IPv4ヘッダー   | UDPヘッダー | VXLANヘッダー | 元のイーサネットフレーム |
| （外側）20B    | 8B       | 8B           | （内側）                  |
+----------------+----------+--------------+---------------------------+
  • VNI（VXLAN Network Identifier）：VXLANヘッダー内の24ビットの識別子。2^24＝16,777,216通り（約1,677万）のL2ネットワークを識別できます。VLAN IDが12ビット（4,096通り）であることとの対比が重要です。
  • UDP：VXLANはUDPでカプセル化します。標準の宛先ポートは4789です。
  • VTEP：VXLANトンネルの端点。カプセル化とカプセル化解除を行います。VTEPのIPアドレスは、トンネルの外側のIPv4ヘッダーの送信元・宛先になります。
  • オーバーヘッド：外側IPv4 20B＋UDP 8B＋VXLAN 8B＋内側イーサネットヘッダー14B＝50B。MTU設計でよく問われる数字です。
MINI QUIZ VXLANカプセル化の順番

外側（トンネルの入口）から内側へ、4つの層を順番にクリックしてください。

外側（トンネル入口）内側（元のフレーム）
？→？→？→？
いちばん外側は「宛先 IP アドレス」を運ぶヘッダー。いちばん内側は、もともと送りたかったフレームです。

図4の対応表の読み方

現行の検証NWでは、VLANとVNI、マルチキャストグループが次のように対応しています。

VLAN ID VNI BUM用マルチキャストグループ 所属するVM
110 10010 239.0.0.1 VM11、VM21、VM31
120 10020 239.0.0.2 VM12、VM22、VM32
130 10030 239.0.0.3 VM13、VM23、VM33

ここが問1の最重要ポイントです。同じVLAN ID（＝同じVNI）のVM同士だけが同じL2ネットワークに属し、L2通信できます。VM11・VM21・VM31は物理的に別のL3SW配下にありますが、VNI 10010を共有するため同じL2セグメントとして通信できます。

VTEPのIPアドレスは各L3SWのループバックインタフェースのIPです。

機器 ループバック（VTEP）IP
L3SW11 10.0.0.11
L3SW12 10.0.0.12
L3SW21 10.0.0.21
L3SW22 10.0.0.22
L3SW31 10.0.0.31
L3SW32 10.0.0.32

BUMフレームとマルチキャスト

VXLANでは、宛先が分からないフレームをBUM（Broadcast、Unknown Unicast、Multicast）として扱い、フラッディングします。現行NWでは、BUMフレームの外側IPv4宛先にVNIごとのIPマルチキャストグループアドレスを設定し、同じグループに参加するVTEPへ転送します。

  • ブロードキャスト（ARP要求など）は、同じL2セグメントの全員に届ける必要がある。
  • ただし、無関係なVNI（別テナント）のVTEPにまで届けてはいけない。
  • そこで「VNIごとのマルチキャストグループ」を使い、同じVNIを持つVTEPだけに届ける。

EVPNの役割

EVPNは、VXLANのコントロールプレーンを担う技術です（RFC 7432、RFC 8365）。データプレーンはVXLANのままです。

  • MP-BGPを使って、リモートVTEPのIPアドレス、VNI、MACアドレス、ESIなどの情報をあらかじめ交換します。
  • 代表的なルートタイプ：
  • Type 2：MAC/IPアドレスルート（VMのMACとVTEPの対応を広告）
  • Type 3：Inclusive Multicast Ethernet Tagルート（BUM転送用のVTEP集合）
  • Type 5：IPプレフィックスルート（L3ルーティング用）
  • これにより、データプレーンの「フラッディングして学習する」処理を減らせます。

1.3 設問1：VXLANの概要

(1) a・b・c

解答：a＝24、b＝3、c＝UDP

  • a：VNIは24ビット。2^24＝16,777,216で「約1,677万個」という本文の記述と一致します。
  • b：VXLANは「レイヤー2のオーバーレイ」を「レイヤー3のIPネットワーク」上に構成します。したがってbは3です。
  • c：カプセル化の順序は「IPv4ヘッダー → UDPヘッダー → VXLANヘッダー → イーサネットフレーム」。よってcはUDPです。

採点講評では、設問1(1)cの正答率が低かったとされています。VXLANがUDPでカプセル化されること、そしてパケット構造の順序を正確に覚えておきましょう。「TCPではない」ことが問われた基本問題です。

(2) ①〜③の情報が含まれるヘッダー

解答：①イーサネットフレーム、②VXLANヘッダー、③IPv4ヘッダー

情報 含まれる場所 理由
①リモートVTEPに接続されたサーバのMACアドレス イーサネットフレーム 元のL2フレームの送信元MACアドレス。VTEPはこれを内側フレームから学習する。
②VXLANトンネルのVNI VXLANヘッダー VNIはVXLANヘッダー内の24ビットフィールド。
③リモートVTEPのIPアドレス IPv4ヘッダー トンネルの外側IPヘッダーの送信元／宛先IPアドレス。

「MACアドレス＝イーサネットフレーム」「VNI＝VXLANヘッダー」「VTEPのIP＝外側IPv4ヘッダー」と、カプセル化の階層で整理すると迷いません。

(3) BUMフレームをマルチキャストで転送する目的

解答：同じレイヤー2のネットワークをもつ全てのリモートVTEPに転送するため

BUMフレームは、宛先がブロードキャスト・未知のユニキャスト・マルチキャストのいずれかで、通常のユニキャスト転送ができません。しかし、VXLANの外側でIPブロードキャストを使ってしまうと、関係のないVNIのVTEPにも届いてしまいます。

そこで、VNIごとに対応するIPマルチキャストグループを用意し、そのグループに参加しているVTEP（＝同じVNI＝同じL2ネットワークを持つVTEP）だけに転送します。これが「同じレイヤー2のネットワークをもつ全てのリモートVTEPに転送するため」という答えです。

1.4 設問2：現行の検証NW（OSPF）

(1) d・e

解答：d＝LSDB、e＝最短経路

  • OSPFはリンクステート型のルーティングプロトコルです。各ルータがLSA（Link State Advertisement）を交換し、それらを集めたLSDB（Link State Database）を作ります。
  • LSDBを基に、自分を根とする最短経路ツリー（SPT）をダイクストラ法（SPF）で計算し、ルーティングテーブルに登録します。

採点講評では、設問2(1)eの正答率が低かったとされています。「SPF」と書きたくなるかもしれませんが、空欄は「〜ツリー」なので「最短経路」が適切です。

(2) ルータIDが識別するもの

解答：OSPFが動作する各L3SW

OSPFのルータIDは、LSAなどの制御情報に含まれ、OSPFを動作させるルータ（ここではL3SW）を一意に識別するための32ビットの識別子です。

K社ではループバックインタフェースのIPアドレスをルータIDにしています。ループバックは物理リンクの状態に左右されず安定しているため、ルータIDが変わりにくいという利点があります。

(3) ECMPを使うための設計

解答：複数ある経路のそれぞれの経路について、コストの合計値を同じ値にする。

ECMP（Equal-Cost Multipath）は、同じ宛先に対してコストが等しい複数の経路がある場合に、それらを同時に使って負荷分散する仕組みです。

OSPFのコストは、各リンクのコスト（デフォルトでは参照帯域幅÷インタフェース帯域幅）の合計で決まります。複数経路の合計コストが異なると、最小コストの経路だけが選ばれ、ECMPは働きません。したがって、設計段階で各経路の合計コストを同じ値に揃える必要があります。

あわせて、ルータ側でECMPを有効にし、最大パス数を必要な数以上に設定しておくことも実務では重要です。

(4) VTEPのIPにループバックを使う理由

解答：一つの物理インタフェースに障害があってもVTEPとして動作できるから

VTEPのIPアドレスは、VXLANパケットの外側の送信元・宛先になります。もし物理インタフェースのIPアドレスをVTEPに使うと、そのリンクがダウンした瞬間にVTEPのIPアドレスが到達不能になり、VXLANトンネルやMAC学習が破綻します。

ループバックインタフェースは、物理リンクがダウンしてもアップ状態を保ち、OSPFなどの代替経路を通じて到達可能です。そのため、1本の物理リンクが故障してもVTEPとして動作し続けられるのです。

1.5 設問3：現行NWのVTEPの動作

(1) ARP要求のVXLANパケットの宛先IPアドレス

解答：239.0.0.1

VM11はVLAN 110、VNI 10010に属します。ARP要求はブロードキャスト（BUM）なので、VNI 10010に対応するマルチキャストグループアドレスが外側IPv4の宛先になります。図4の対応表から、VLAN 110／VNI 10010のグループアドレスは239.0.0.1です。

(2) L3SW31が学習する情報

解答：VM11のMACアドレス、VNI及びL3SW11のVTEPのIPアドレス

L3SW31は、L3SW11からARP要求を含むVXLANパケットを受信します。このとき、内側フレームの送信元MACアドレス、VXLANヘッダーのVNI、外側IPv4ヘッダーの送信元IPアドレスを組み合わせて学習します。

  • 内側フレームの送信元MACアドレス → VM11のMACアドレス
  • VXLANヘッダーのVNI → 10010
  • 外側IPv4ヘッダーの送信元IPアドレス → L3SW11のVTEPのIPアドレス（10.0.0.11）

「VM11のIPアドレス」ではないことに注意してください。VTEPが学習するのはMACアドレスとVNIとリモートVTEPのIPです。

(3) 表2のキ〜コ

解答：キ＝10010、ク＝10.0.0.31、ケ＝10010、コ＝10.0.0.11

表2は、ARP通信の完了後にL3SW11とL3SW31が学習した内容です。向きを整理します。

機器 学習するVMのMAC VNI リモートVTEPのIP
L3SW11 VM31のMACアドレス 10010 L3SW31のVTEP＝10.0.0.31
L3SW31 VM11のMACアドレス 10010 L3SW11のVTEP＝10.0.0.11
  • L3SW11は、L3SW31から届いたARP応答（VM31のMACを含む）から、VM31のMAC、VNI 10010、リモートVTEP＝L3SW31（10.0.0.31）を学習します。
  • L3SW31は、L3SW11から届いたARP要求（VM11のMACを含む）から、VM11のMAC、VNI 10010、リモートVTEP＝L3SW11（10.0.0.11）を学習します。

採点講評では、クとコの正答率がやや低く、「クとコが逆」「VMのIPアドレスを書いてしまう」誤答が散見されたとあります。「学習する側から見て、相手のVTEPはどちらか」を必ず確認しましょう。

1.6 設問4：新検証NW（EVPN）

(1) ルートリフレクタの利点とループ防止ID

解答：利点＝iBGPピアの数を減らすことができる。／名称＝クラスターID

iBGPは、同一AS内のBGPルータ同士で経路を交換しますが、原則としてフルメッシュのピアリングが必要です。ルータ数がn台だと、ピア数はn(n−1)/2と急増します。

ルートリフレクタ（RR）を置くと、各ルータはRRとだけiBGPピアを張り、RRが経路を反射（リフレクト）します。これによりiBGPピアの数を大幅に減らせます。

RRを冗長化して複数台置く場合、同じ経路が複数のRRから反射されてループする可能性があります。これを防ぐために、同じクラスタに属するRRに同じクラスターIDを設定します。RRは経路にクラスターIDを付加し（CLUSTER_LIST）、自分と同じクラスターIDを含む経路は再反射しません。

採点講評では設問4(1)の正答率が低く、BGPの理解を深めてほしいとされています。RRの利点は「ピア数削減」、冗長化時のループ防止は「クラスターID」とセットで覚えましょう。

(2) f・g

解答：f＝Unknown Unicast、g＝ESI

  • f：BUMのうち「U」はUnknown Unicastです。EVPNの機能2では、MP-BGPであらかじめMACアドレスとVTEPの対応を学習するため、未知のユニキャスト宛てフレームをフラッディングせず、学習したVTEPへユニキャスト転送できます。
  • g：ESI（Ethernet Segment Identifier）。同じ物理サーバに接続する複数のVTEPの論理インタフェースに同じESIを設定すると、それらを1つのEthernet Segmentとして扱えます。これにより、サーバと複数VTEPの間でリンクアグリゲーション（マルチホーミング）が可能になります。

(3) アクティブ／アクティブ構成の利点

解答：二つの回線の帯域を有効に利用できる。

現行NWのNICはアクティブ／スタンバイ構成で、通常は片方の回線しか使いません。もう片方は待機用なので、帯域が遊んでいます。

新検証NWでは、EVPNの機能3（ESI）によって複数VTEPとサーバの間でリンクアグリゲーションを組めるため、アクティブ／アクティブで両方の回線を同時に使えます。結果として、2本の回線の帯域を有効に利用でき、負荷分散と冗長性を両立できます。

(4) リモートVTEPのIPアドレスの学習方法

解答：MP-BGPを用いて学習する。

現行NWでは、VTEPは受信したVXLANパケットの外側IPv4ヘッダーからリモートVTEPのIPアドレスを学習していました（データプレーン学習）。

新検証NWではEVPNを適用し、MP-BGPでリモートVTEPのIPアドレスやVNIをあらかじめ交換します（コントロールプレーン学習）。これにより、最初の通信からユニキャストで転送でき、フラッディングを減らせます。

(5) ARP要求フレームの転送先

解答：VLAN IDに対応するVNIをもつ全てのリモートVTEP

新検証NWでは、BUMフレームの転送にIPマルチキャストではなくIPユニキャストを使います。ARP要求を受け取ったVTEPは、フレームのVLAN IDをVNIに変換し、そのVNIを持つ全てのリモートVTEPを宛先として、それぞれにユニキャストでVXLANパケットを送ります。

  • 「全てのVTEP」ではない：無関係なVNIのVTEPには送らない。
  • 「1台のVTEP」でもない：ARP要求は宛先が未知なので、同じL2セグメントの全VTEPに届ける必要がある。

この「VNIごとのVTEP集合をMP-BGPで把握し、ユニキャストで複製送信する」点が、EVPN適用後のBUM転送の特徴です。

1.7 問1のまとめ

問1は、VXLANのデータプレーンとEVPNのコントロールプレーンを対比させる構成でした。押さえるべき軸は次の4つです。

  1. カプセル化の階層：内側イーサネット／VXLAN（VNI）／UDP／外側IPv4。どの情報がどのヘッダーにあるか。
  2. VNIとL2セグメントの対応：同じVNI＝同じL2ネットワーク。通信可否もBUMの転送先もこれで決まる。
  3. アンダーレイの安定性：OSPFのLSDB・SPF・ECMP、ループバックをVTEPに使う理由。
  4. EVPNによる変化：データプレーン学習→MP-BGPによる事前学習、マルチキャスト→ユニキャスト複製、ESIによるマルチホーミング、RRによるiBGPピア削減。

問2 電子メールを用いた製品サポート（SPF／DKIM／S/MIME）

2.1 出題の狙い

出題趣旨は、標的型メール攻撃が巧妙化し、なりすましメールによる被害が増えていることを背景に、メールによるサポート業務を他社に委託する場面を取り上げ、送信ドメイン認証（SPF／DKIM）とS/MIMEの導入検討にネットワーク技術を活用できるかを問うものです。

問2の特徴は、DNSのゾーン情報とFWのNAT設定からメールの配送経路を復元する点にあります。技術用語の暗記だけでなく、「どのサーバが、どの名前を解決し、どのIPから送信し、受信側が何を検証するか」を図から追えるかが勝負です。

2.2 図表の整理（配送経路の復元）

Y社のネットワーク

  • 社内メールサーバY：社内のユーザーが使うメールサーバ。サポート担当者はここから送信する。
  • メール中継サーバY1／Y2：DMZにあり、社内と社外のメールを中継する。メールボックスは持たない。
  • 外部DNSサーバY（y-ns1）：y-sha.comの権威DNS。MX、SPF、DKIMなどの対外情報を管理。
  • 社内DNSサーバY（y-ns2）：社内ゾーン（y-sha.lan）を管理。
  • FW：インターネットからDMZへの通信に静的NATを設定。

外部DNSサーバYのゾーン情報（対外）

y-sha.com.        IN MX  1 y-mail2.y-sha.com.
y-mail1.y-sha.com. IN A 200.a.b.1
y-mail2.y-sha.com. IN A 200.a.b.2
  • MXのPreference値は小さいほど優先度が高い。平常時は1のy-mail2が選ばれ、障害時は20のy-mail1が使われます。

社内DNSサーバYのゾーン情報（社内）

y-mail3.y-sha.lan.  IN A 192.168.1.1
mail.y-sha.lan. 60  IN A 192.168.0.1
mail.y-sha.lan. 60  IN A 192.168.0.2
y-mail1.y-sha.lan.  IN A 192.168.0.1
y-mail2.y-sha.lan.  IN A 192.168.0.2
  • mail.y-sha.lanはAレコードが2つあり、TTLが60秒と短く設定されています。これがDNSラウンドロビン用の名前です。

FWの静的NAT

y-mail1.y-sha.com 200.a.b.1 192.168.0.1
y-mail2.y-sha.com 200.a.b.2 192.168.0.2

メールの流れ

  1. サポート担当者が社内メールサーバYから送信する。
  2. 社内メールサーバYは、社内DNSでmail.y-sha.lanを解決する。Aレコードが2つあるため、DNSラウンドロビンでY1またはY2に振り分けられる。
  3. Y1／Y2がDKIM署名を付与し、インターネット経由で顧客のメールサーバへ送信する。

  1. 顧客のメールサーバがy-sha.comのMXを引く。Preferenceが小さいy-mail2（200.a.b.2）が選ばれる。
  2. FWの静的NATで200.a.b.2→192.168.0.2に変換され、メール中継サーバY2に届く。
  3. Y2から社内メールサーバYへ転送される。

Z社のネットワーク

  • 外部DNSサーバZ（z-ns1）：z-sha.co.jpの権威DNS。

  • 社内メールサーバZ（z-mail2）：Z社のサポート担当者が使うメールサーバ。

2.3 設問1：Y社のネットワーク構成とセキュリティ対策の背景

(1) 転送先のメール中継サーバのFQDN

解答：mail.y-sha.lan

社内メールサーバYが社外宛てメールを中継サーバY1／Y2へ転送するとき、社内DNSで解決する名前がmail.y-sha.lanです。この名前には192.168.0.1と192.168.0.2の2つのAレコードがあり、DNSラウンドロビンでY1／Y2に振り分けられます。

y-mail1.y-sha.comやy-mail2.y-sha.comは、外部からの受信時にMXレコードが指す名前です。社内からの送信で使う名前と、外部からの受信で使う名前を混同しないことがポイントです。

(2) 振り分けの偏りを小さくする方策

解答：TTLを60秒と短い値にしている。

DNSラウンドロビンは、名前解決のたびに複数のAレコードを順番に返すことで負荷分散します。しかし、リゾルバは返された回答をTTLの間キャッシュします。TTLが長いと、同じIPアドレスがキャッシュされ続け、特定の中継サーバに偏ります。

mail.y-sha.lanのTTLを60秒と短くすることで、キャッシュの寿命が短くなり、社内メールサーバYは頻繁に再問い合わせします。その結果、ラウンドロビンが機能し、振り分けの偏りが小さくなります。

採点講評でも、設問1(2)の正答率が低かったとされています。「送信元が社内メールサーバYだけ」という構成では、短いTTLが特に重要になる、という理由まで理解しておきましょう。

(3) a・b・c

解答：a＝Preference、b＝y-mail2、c＝逆引き

  • a：MXレコードの優先度はPreference（プリファレンス）です。値が小さいほど優先されます。
  • b：平常時に選ばれるのはPreferenceが1のy-mail2です。
  • c：IPアドレスからFQDNを引く名前解決は逆引き（PTRレコード）です。

(4) ア・イ

解答：ア＝200.a.b.1、イ＝192.168.0.1

表1の1行目はy-mail1のNATです。

  • 宛先IPアドレス（グローバル）：200.a.b.1
  • 変換後のIPアドレス（DMZの実アドレス）：192.168.0.1

静的NATは、インターネットからDMZのサーバへ届けるために、グローバルIPをプライベートIPに1対1で変換します。

(5) 攻撃者がPTRレコードに行う不正な操作

解答：メールサーバのFQDNに、詐称したメールアドレスのドメイン名を登録する。

逆引きを使った素朴な判定では、送信元メールサーバのIPアドレスからPTRでFQDNを取得し、そのFQDNのドメイン名と送信元メールアドレスのドメイン名が一致するかを見ます。

攻撃者は、自分が管理するDNSサーバのPTRレコードに、詐称したいドメイン名を持つFQDNを登録できます。すると、逆引きの結果が詐称先のドメインに見えてしまい、素朴な判定を通過してしまいます。

これを防ぐには、PTRで得たFQDNをさらに正引きし、元のIPアドレスと一致するか確認するFCrDNS（Forward-confirmed reverse DNS）が有効です。ただし、それでもドメイン認証としては不十分で、SPFやDKIMが必要になります。

2.4 設問2：SPF

(1) ウ・エ

解答：ウ＝200.a.b.1、エ＝200.a.b.2

SPFレコードは、そのドメインのメールを送信してよいサーバのIPアドレスを列挙します。Y社の送信元はメール中継サーバY1／Y2なので、それぞれのグローバルIPである200.a.b.1と200.a.b.2を登録します。

図4のレコードは次の形です。

y-sha.com. IN TXT "v=spf1 +ip4:200.a.b.1 +ip4:200.a.b.2 -all"
  • v=spf1：SPFのバージョン。
  • +ip4:...：そのIPv4アドレスからの送信を許可（Pass）。
  • -all：上記以外の送信元は失敗（Fail）とする。

(2) d・e・f

解答：d＝SMTP、e＝MAIL FROM、f＝y-sha.com

  • d：メール転送プロトコルはSMTPです。
  • e：SPFが参照する送信元は、SMTPのMAIL FROMコマンドで指定されるエンベロープ送信者アドレスです。
  • f：support@y-sha.comのドメイン名はy-sha.comです。

ここで重要なのは、エンベロープのMAIL FROMと、メールヘッダーのFromは別物という点です。SPFは原則としてMAIL FROM（およびHELO）のドメインと、実際の接続元IPアドレスを照合します。ヘッダーFromの表示名やアドレスを直接保証するものではありません。

(3) 正当性の確認方法

解答：送信元のメールサーバのIPアドレスが、SPFレコードの中に登録されていること

受信側のメールサーバは、SMTP接続してきた相手の実際の送信元IPアドレスを取得します。次に、MAIL FROMのドメイン（y-sha.com）のSPFレコードをDNSから取得し、その中のip4などの機構に、実際の送信元IPアドレスが含まれているかを確認します。

含まれていればPass、含まれていなければFail（-allの場合）となります。SPFは「IPアドレスベース」の認証であり、メールの本文やヘッダーの中身を検証するものではない、という特徴を押さえましょう。

2.5 設問3：DKIM

(1) g・h・i

解答：g＝ヘッダー、h＝UDP、i＝512

  • g：DKIMの電子署名は、メールのヘッダー（DKIM-Signatureのhタグで指定されたヘッダー群）と本文を基に生成されます。
  • h：DNSをトランスポートするプロトコルは、通常UDPです。
  • i：従来のDNSメッセージの最大長は512バイトです（EDNS0を使わない場合）。

DKIMレコードには公開鍵をBase64で格納します。2048ビットのRSA公開鍵は、Base64やDNSのオーバーヘッドを含めても512バイトに収まるため、UDPのDNSで取得できます。これより大きい鍵（例：4096ビット）は512バイトを超え、TCPへのフォールバックや分割が問題になることがあります。

(2) 暗号化方式のアルゴリズム名と鍵名

解答：アルゴリズム名＝RSA、オ＝公開鍵

図5のDKIMレコードは次の形です。

sel.ysha._domainkey.y-sha.com. IN TXT "v=DKIM1; k=rsa; t=s; p=（公開鍵）"
  • k=rsa：鍵の形式はRSA。
  • p=...：Base64でエンコードされた公開鍵。

DKIMは公開鍵暗号を使います。送信側は秘密鍵で署名し、受信側はDNSに公開された公開鍵で署名を検証します。秘密鍵は送信側だけが保持します。

(3) 電子署名の真正性でなりすましが分かる理由

解答：受信したメールが正規のメールサーバから送信されたものかどうかが分かるから

DKIMの署名は、正規の送信側だけが持つ秘密鍵で生成されます。受信側がDNSから取得した公開鍵で署名を検証し、正しく検証できれば、そのメールは秘密鍵を持つ正規のメールサーバ（ここではY社のメール中継サーバY1／Y2）で署名されたことになります。

つまり、DKIMの検証成功は「正規のドメインの署名サーバから送られた」ことの証明になり、なりすましメールではないと判断できます。あわせて、本文やヘッダーが改ざんされていないことも確認できます。

採点講評では設問3(3)の正答率が低かったとされています。「改ざんされていない」だけでなく、「正規のメールサーバから送信されたことが分かる」という送信元認証の側面を書くことが重要です。

2.6 設問4：Z社への委託

(1) 登録するDNSサーバ名と情報

解答：DNSサーバ名＝外部DNSサーバY（y-ns1）／登録する情報＝メール中継サーバZのIPアドレス（z-mail1のIPアドレス）

Z社からsupport@y-sha.comとして送信する場合でも、SPFの検証対象ドメインはy-sha.comです。したがって、y-sha.comのSPFレコードに、Z社の送信元IPアドレスを追加する必要があります。

  • y-sha.comの権威DNSは外部DNSサーバY（y-ns1）です。SPFレコード（TXT）はここに登録します。
  • 追加する情報は、Z社の送信元であるメール中継サーバZ（z-mail1）のIPアドレスです。図7からz-mail1は222.c.d.1なので、実際にはip4:222.c.d.1を追加することになります。

社内DNSサーバY（y-ns2）はy-sha.lanの内部ゾーン用であり、対外ドメインy-sha.comのSPF公開場所ではありません。ここを間違えないようにしましょう。

(2) j

解答：y-sha.com

DKIM-Signatureのd=タグは、署名したドメイン名を示します。顧客のメールサーバは、このd=のドメインのDKIMレコードをDNSで引きます。顧客が使う権威DNSは外部DNSサーバYなので、d=はy-sha.comでなければなりません。

セレクター名s=はsel.zshaとし、Y社本体が使うsel.yshaとは別の鍵を使います。DKIMレコードの名前は次のようになります。

sel.zsha._domainkey.y-sha.com. IN TXT "v=DKIM1; k=rsa; p=（Z社用の公開鍵）"

(3) 異なる鍵を使うセキュリティ上の利点

解答：メール中継サーバZから鍵が漏えいしても、Y社で実施中のDKIMの処理は影響を受けない。

Y社本体はsel.ysha、Z社はsel.zshaと、セレクターごとに別の鍵を使います。もしZ社側の秘密鍵が漏えいしても、影響を受けるのはsel.zshaの署名だけです。Y社本体のsel.yshaの秘密鍵は別なので、Y社が送信するメールのDKIM処理は継続できます。

また、漏えい時にはsel.zshaのDKIMレコードを削除・無効化すれば、Z社用の署名だけを失効させられます。鍵の影響範囲を局所化できることが、セレクターを分ける最大の利点です。

(4) 委託先の内部者によるなりすましを検知できない理由

解答：なりすましメールも、メール中継サーバZから社外に転送されるから

Z社のサポートチームY以外の部署の従業員が、送信元メールアドレスをsupport@y-sha.comに偽装して送信したとします。このメールも、Z社のメール中継サーバZを通って社外に転送されます。

メール中継サーバZは、support@y-sha.comからのメールに対してDKIM署名（sel.zsha）を付与します。また、送信元IPはZ社の中継サーバZなので、SPFもPassします。その結果、顧客のメールサーバでは、SPFもDKIMも「正常」と判定され、なりすましを検知できません。

つまり、SPF／DKIMはドメイン単位・サーバ単位の認証であり、「そのドメインの正規のメールサーバを通ったか」は分かっても、「送信した個人が本当にサポート担当者か」までは分からないのです。ここを補うのが、個人の電子証明書を使うS/MIMEです。

2.7 設問5：S/MIME（問題不備）

公式の扱い

IPAは2024年6月7日付で「設問5の不備とその対応について」を公表しました。ネットワークスペシャリスト試験の午後II 問2 設問5(1)〜(3)について問題不備が認められ、当該大問を選択した受験者は設問5を全員正解として扱うことになりました。解答例でも「不備により設問5(1)〜(3)は成立しない」とされています。

何が問題だったのか

問題の表4は、電子署名の手順を次のように説明していました。

  1. ハッシュ関数hでメール内容のハッシュ値aを生成する。
  2. ハッシュ値aを基に電子署名データを作成する。
  3. 電子証明書と電子署名付きメールを送信する。
  4. 受信したメールの電子署名データからハッシュ値aを取り出す。
  5. ハッシュ関数hでメール内容のハッシュ値bを生成する。
  6. ハッシュ値を比較する。

この記述には、次の問題があります。

  • 「電子署名データからハッシュ値aを取り出す」はRSA固有の性質です。ECDSAやEdDSAなどの署名方式では、署名から元のハッシュ値を復元するような処理はありません。S/MIMEはRSA以外の署名方式も扱えるため、一般性がありません。
  • S/MIME（CMS）の署名対象は、メール本文そのものではなく、署名対象属性群（signedAttrs）です。本文のハッシュ値はその属性の1つに過ぎず、署名日時などの属性を含めたデータに対して署名が計算されます。
  • そのため、「電子署名データからハッシュ値aを取り出す」という手順は、S/MIMEの仕様に沿った説明ではありません。また、公開鍵を使った署名検証の記述が抜けています。

結果として、本文の記述だけでは解答を一意に導けず、問題として成立しないと判断されました。

試験対策として、一般的な教科書的な理解（RSAを前提とした簡略モデル）を整理しておきます。予備校の参考解答も、このモデルに沿っています。

(1) 電子署名データの作成方法 ハッシュ値aを送信者の秘密鍵で暗号化する。
(2) ハッシュ値aを取り出す方法 送信者の公開鍵で電子署名データを復号する。
(3) 改ざんされていないと判断できる状態 ハッシュ値aとハッシュ値bが一致する。

ただし、これはあくまでRSAの簡略モデルです。正確には、デジタル署名は次のような仕組みです。

  • 署名生成：メッセージのハッシュ値を計算し、署名アルゴリズム（RSAならRSASP1、ECDSAなら楕円曲線演算など）を送信者の秘密鍵で適用して署名値を作る。
  • 署名検証：受信側でメッセージのハッシュ値を計算し、署名値を送信者の公開鍵で検証アルゴリズム（RSAならRSAVP1など）にかけ、期待されるハッシュ値と一致するか確認する。
  • S/MIMEの実際：署名対象属性群（signedAttrs）に対して署名を検証し、その中の本文ハッシュと、受信した本文から計算したハッシュが一致することを確認する。

「秘密鍵で暗号化する」という表現はRSAの内部処理に近い説明で、すべての署名方式に通用するわけではありません。「秘密鍵で署名し、公開鍵で検証する」という本質を押さえ、方式ごとの違いがあることを理解しておきましょう。

2.8 問2のまとめ：SPF・DKIM・S/MIMEの比較

方式 認証する単位 主な要素 検証する主体 守れる範囲 主な限界
SPF エンベロープのドメイン（MAIL FROM）と送信元IP DNSのTXT（SPFレコード） 受信側メールサーバ 送信元サーバの正規性（IPベース） 転送で壊れやすい。ヘッダーFromは保証しない。
DKIM 署名ドメイン（d=）とメール内容 DKIM-Signatureヘッダー、DNSの公開鍵 受信側メールサーバ ドメインの正規性と改ざん検知 個人の識別はしない。鍵管理が必要。
DMARC FromドメインとSPF／DKIMのアライメント DNSのDMARCレコード、ポリシー 受信側メールサーバ なりすまし対策の運用（失敗時の扱い、報告） 準拠していない送信者には効果が限定的。
S/MIME 個人（送信者）の電子証明書 電子証明書、秘密鍵、MUA 受信者のMUA エンドツーエンドの署名・暗号化、個人の識別 証明書配布・管理の手間。全員が対応しているとは限らない。

問2の要点は、「ドメイン認証（SPF／DKIM）」と「個人認証（S/MIME）」の守備範囲の違いです。SPF／DKIMだけでは、委託先の別部署の従業員によるなりすまし（正規の中継サーバを通るもの）を防げません。そこをS/MIMEの個人証明書で補う、という設計思想を理解しましょう。

3. 学習アドバイス

問1（VXLAN／EVPN）

  1. カプセル化を図で描けるようにする
    「内側イーサネット → VXLAN → UDP → 外側IPv4」の順序と、各ヘッダーに何が入るかを白紙に描いてみましょう。特にVNIが24ビット、UDPの標準ポートが4789、オーバーヘッドが50バイト、という数字は狙われます。

  2. VNIとL2セグメントの対応表を自分で作る
    図4のようなVLAN／VNI／グループアドレスの表から、通信可否やBUMの転送先を導けるようにします。「同じVNI＝同じL2」がすべての基準です。

  3. データプレーン学習とコントロールプレーン学習を対比する
    現行VXLAN：受信パケットからMAC・VNI・VTEP IPを学習。EVPN：MP-BGPで事前学習。この違いが、Unknown Unicastの削減、マルチキャスト→ユニキャスト複製、ESIによるマルチホーミングにつながります。

  4. OSPFとBGPの基礎を押さえる
    LSDB、SPF、ECMP、ルータID、ループバック、iBGPのフルメッシュ、ルートリフレクタ、クラスターID。問1はL2だけではなく、アンダーレイのL3技術も問われます。

問2（メール認証）

  1. DNSゾーンとNATから配送経路を復元する
    「誰が」「どの名前を」「どのDNSで」解決し、「どのIPから」送信するのかを、図を見ながら時系列で追います。MXのPreference、AレコードのTTL、静的NATの対応を正確に読み取ることが第一歩です。

  2. エンベロープとヘッダーを区別する
    SPFはMAIL FROM（エンベロープ）と接続元IPを見ます。ヘッダーFromとは別物です。この区別が、なりすまし検知の限界やDMARCの必要性につながります。

  3. SPF・DKIM・S/MIMEの守備範囲を整理する
    SPF＝IPベースのサーバ認証、DKIM＝ドメインの署名認証、S/MIME＝個人の証明書認証。それぞれ何を守り、何を守れないかを表にして覚えましょう。

  4. 鍵とセレクターの分離を理解する
    DKIMのセレクターは、同じドメインで複数の鍵を使い分けるための仕組みです。委託先と自社で鍵を分けることで、鍵漏えい時の影響を局所化できます。

  5. 問題不備の設問は「Why」まで確認する
    設問5は試験としては不成立でしたが、デジタル署名の仕組みを学ぶ教材としては有用です。「秘密鍵で暗号化」という単純化が、なぜ一般には正しくないのか。RSAとECDSAの違い、S/MIMEの署名対象（signedAttrs）まで踏み込んで理解しておくと、他の午後問題にも応用できます。
