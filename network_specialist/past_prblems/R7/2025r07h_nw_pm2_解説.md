# 問1 社内ネットワークのIPv6対応

## 前提となる知識

### 1. ARP と NDP の対応関係

| IPv4 | IPv6 | 役割 |
|---|---|---|
| ARP リクエスト（ブロードキャスト） | NS（Neighbor Solicitation）マルチキャスト | 宛先IPに対応するMACを問い合わせる |
| ARP リプライ | NA（Neighbor Advertisement）ユニキャスト | 自身のMACを通知する |
| （ブロードキャスト / DHCP） | RS / RA | ルータ探索・プレフィックス通知・デフォルトルータ通知 |

NDP（RFC 4861）は NS/NA に加え RS/RA を用い、以下を実現します。

- データリンク層で通信可能な範囲のルータを発見
- サブネットプレフィックス・デフォルトルータの通知
- 重複アドレス検出（DAD: Duplicate Address Detection）

### 2. IPv6アドレス体系（RFC 4291 / 4862）

- 128ビット、16ビットずつを `:` で区切って表記（hextet）
- **LLA（リンクローカル）**: `fe80::/64`。同一リンク内のみ有効
- **GUA（グローバル）**: ISPから `/48` または `/56` を割り当てられ、 `/64` のサブネットに分割して利用
- インタフェース識別子（下位64ビット）の生成方法:
  - 疑似乱数によるランダム生成（推奨・プライバシー保護向き）
  - MAC(48bit) → Modified EUI-64(64bit)（固定で識別しやすいため非推奨）

### 3. SLAAC によるアドレス生成の流れ（図3）

1. 仮LLAを生成し NS を送って応答が無いことを確認（DAD）
2. 正式なLLAを NA で全ノードマルチキャストへ通知
3. RS を全ルータマルチキャストへ送信
4. ルータが RA（プレフィックス＋デフォルトルータ情報）を応答
5. 仮GUAを生成し NS でDAD
6. 正式なGUAを NA で通知
7. RAの送信元（ルータ）のLLAをデフォルトルータに設定

### 4. EDNS と DNS メッセージサイズ

IPv6アドレス（AAAAレコード）はIPv4より大きく、512バイトを超えるDNSメッセージが珍しくありません。EDNS0（RFC 6891）で UDP 上のサイズ上限を緩和し、それでも収まらない場合や相手がEDNS非対応の場合は **TCP** に切り替えます。

## 設問2 IPv6アドレスの割当て

### (1) 数値 d〜f

| 空欄 | 解答 | 根拠 |
|---|---|---|
| d | **16** | IPv6は16ビット（hextet）ずつ `:` で区切って表記 |
| e | **48** | ISPから割り当てられるGUAのプレフィックス長（48 または 56） |
| f | **64** | サブネット分割後のプレフィックス長。インタフェースIDも64ビット |

※ 本文の「128ビット構成」「MACアドレス48ビット → Modified EUI-64」も併せて確認。

### (2) LLAが有効な範囲（30字以内）

**「データリンク層で通信可能な範囲」**

LLAは `fe80::/64` でルータを越えられません。OSPFv3がLLAをネクストホップに使えるのも、この「同一リンク内」という性質のためです。

### (3) 処理(i)および(v)の目的（55字以内）

**「同じデータリンク層上に同じIPv6アドレスを使用しているノードがいないことを確認するため」**

どちらも仮アドレスを NS で問い合わせ、NA が返ってこないことで重複がない（DAD成功）を確認しています。

### (4) 仮GUAとプレフィックス長

- 正式LLA: `fe80::8:800:200c:417a`
- RAのプレフィックス: `2001:db8:aabb:1::/64`

LLAの下位64ビット `0008:0800:200c:417a` をインタフェースIDとして再利用するため:

| 項目 | 解答 |
|---|---|
| 仮GUA | **`2001:db8:aabb:1:8:800:200c:417a`** |
| プレフィックス長 | **64** |

> 語尾の `8:800:200c:417a` をそのままコピーするのがコツです。

### (5) 空欄 g

**「デフォルトルータ」**（または「デフォルトゲートウェイ」）

RAの送信元であるルータ（ノード③＝L3SW①）のLLAを、PCはデフォルトルータとして設定します。DHCPが無くてもSLAACでゲートウェイが分かる点が重要です。

### (6) 下線②の理由（20字以内）

**「PCを特定しづらくなるから」**

ランダムなインタフェースIDはプライバシー保護に有効ですが、MACアドレスからPCを識別できなくなるため、資産管理・ログ追跡・ACL運用での考慮が必要になります。

### (1) 空欄 h

**「TCP」**

EDNS対応済み同士でも、最大メッセージサイズ超過 or 非対応権威サーバとの512バイト超通信では TCP にフォールバックします。

### (2) 図5のAAAAレコード応答

`saas.example.com.` は CNAME で `dual-saas.example.net.` を指しています。

| 求められるもの | 解答 |
|---|---|
| V社SaaSのIPv6アドレス | **`2001:db8:xxxx::10`**, **`2001:db8:xxxx::20`** |

### (3) 下線③の理由（45字以内）

デュアルスタック環境では IPv6 が不通でも A レコード経由で同じページが表示され、利用者も運用者も異常に気付きにくい＝そのため監視サーバからの `ping6` が必要、という流れです。

## 設問4 IPv6ネットワークの設計

### (1) a〜d に GUA を割り当てない目的（50字以内）

**「インターネットからルータA，ルータB及びFWにアクセスできないようにするため」**

インターネット側のインタフェースに GUA を持たせなければ、外部から直接宛先にできません（LLAのみならリンク外から到達不可）。IPv4のNAPTに相当する「隠蔽」をIPv6ではアドレス設計で行う発想です。

### (2) GUAを「静的に」割り当てる利点（45字以内）

**「traceroute6を利用して調べるときに各機器を識別しやすくする」**

経路上のホップが GUA で表示されるため、どのルータ/FW/L3SWを通っているかが一発で分かります。動的なLLAでは `fe80::...` だらけで識別が難しいです。

### (3) 下線⑤のL3SWの動作（40字以内）

**「PCが送信したRSメッセージに対してRAメッセージを応答する」**

PCがSLAACでアドレスとデフォルトルータを自動設定できるのは、L3SWがRAを返すからです。ICMPv6メッセージ名を書くのが採点ポイント。

### (4) 表1の [ア]〜[ケ]

| 空欄 | 解答 | 空欄 | 解答 | 空欄 | 解答 |
|---|---|---|---|---|---|
| ア | `fe80::1` | イ | `b` | ウ | `fe80::2` |
| エ | `c` | オ | `fe80::1` | カ | `d` |
| キ | `fe80::2` | ク | `f` | ケ | `fe80::1` |

**考え方**

- OSPFv3は **LLAをネクストホップ** にして隣接関係を張る → 表中のネクストホップは `fe80::1` / `fe80::2`（ルータA/BのLLA）
- 項番1はISP向けデフォルトルート → ネクストホップはルータA側のLLA
- 項番3・5は拠点①向け、項番4・6はOSPFv3で配布されたデフォルトルート → 対応する出口インタフェース名（b, c, d, f）を図6の a〜h から選ぶ

> 表の「出口が廃棄用インタフェース」になっている行が項番2（後述のヌールート）です。

### (5) 項番2の経路が無い場合の処理（35字以内）

**「ホップリミットが0になるまで相互に転送し合い，廃棄する」**

IPv6にはIPv4のTTLの代わりに **ホップリミット** があります。未使用GUA宛てのパケットがルータA⇔ルータB間でルーティングループし、ホップリミット枯渇で廃棄されます。項番2の「廃棄用インタフェースへの静的経路（ヌールート）」はこれを防ぐためのものです。

### (6) 項番2が選択される理由（25字以内）

**「ロンゲストマッチによって選択されるから」**

項番1（デフォルトルート `/0`）と項番2（未使用GUAを含む `/48`）の両方に一致するパケットは、より長いプレフィックスの項番2が優先されます。

### (7) 空欄 i

**「NAPT」**

IPv4ではルータBのNAPTで内部アドレスを隠していましたが、IPv6ではGUAを直接使うためNAPTを呼びません。だからこそFWのアクセス制御設計を慎重にする必要があります。

### (8) PMTUDで検出されるもの（20字以内）

**「通信経路における最小のMTU」**

中継機器が「Packet Too Big（ICMPv6 Type 2）」を返し、送信元が経路全体で通る最小MTUを学習します。ICMPv6をFWで拒否するとPMTUDが壊れるため、必要なタイプだけ許可するのが実務のポイントです。

# 問2 IoTシステムの設計（LPガス遠隔検針）

## 前提となる知識

### 1. LPWAの分類

| 分類 | 技術 | 特徴 |
|---|---|---|
| **非セルラー**（b） | LoRaWAN, Sigfox | 920MHz帯（ISMバンド）、2.4GHzより電波**干渉**が少ない。事業者網ではなく自前GW |
| **セルラー**（c） | LTE-M (LTE Cat.M), NB-IoT (Cat.NB1) | **3GPP**標準、通信事業者の全国LTE網を利用。SIMで契約者識別 |

低**消費**電力（a）で電池長寿命化を実現するのがLPWAの肝です。

### 2. IPsec / IKEv2

- 図1のIPsecルータ①と②の間で **IKEv2（g=2）** が4メッセージの交換を行い SAD を作成
- SPDのセレクターには **Gメーター管理サーバ（h）** 宛てのパケットをIPsec処理するよう設定
- 閉域網により Gメーター⇔管理サーバはプライベートIPで通信
- Gメーターには **SIM（i）** を装着

### 3. 利用料の試算（j）

```
1か月の通信量 = 100バイト/回 × 24回/日 × 30日 = 72,000バイト
通信費       = 72,000 ÷ 1,000 × 1円 = 72円
基本料金     = 300円
合計         = 72 + 300 = 372円  →  j = 372
```

### 4. CoAP の基礎

- RFC 7252、Web API の **RESTful（k）** アーキテクチャを採用
- 標準は **UDP（トランスポート層=l）**、必要に応じて DTLS（RFC 9147）
- 4種類のメッセージタイプ: **CON / NON / ACK / RST**
- **メッセージID**: 要求・応答の関連付け **＋ 重複検出**
- **トークン**: 「どの要求に対する応答か」を識別（メッセージIDとは役割が異なる）
- パケットロス対策: ACK待ち → タイムアウト → **指数バックオフ（p）** で再送

## 設問3 CoAPの調査

### (1) 用語 l〜p

| 空欄 | 解答 | 補足 |
|---|---|---|
| l | **トランスポート** | UDPはOSI第4層（トランスポート層） |
| m | **順不同** | UDPではパケットの到着順序が保証されない |
| n | **重複** | 同じパケットが二重に到着することがある |
| o | **同期** | メッセージIDで送受信の同期を取る |
| p | **バックオフ** | 指数バックオフで再送間隔を伸ばし、再送が通信を圧迫しないようにする |

### (2) 下線①：(iv)で送れなかったデータが送られるメッセージ

| 項目 | 解答 |
|---|---|
| メッセージ | **ⅷ** |
| 理由（15字以内） | **トークン値が一致するから** |

(iv)は「すぐにデータを返せない」ため空ACKで応答し、後で (ⅷ) の CON にトークン `0x10` を付けてデータZを送ります。(i) の要求トークンと一致するので、どの要求への応答か分かります。

### (3) 下線②：サーバが送信したACK

**「ⅴ」**

(ii) の要求（`0xab20` / トークン`0x20`）に対して、`2.05 Content` を **ピギーバック** した ACK が (v) です。(iv) はデータ未準備の空ACK、(vi)(vii) は別要求への応答。

### (4) 下線③：重複ACKの判断と処理

| 項目 | 解答（各30字以内） |
|---|---|
| 理由 | **二つのパケットのメッセージIDが同じだから** |
| 処理 | **受信した(ⅶ)のACKは処理済みなので無視する。** |

(vi) と (vii) はどちらも Message ID `0xde10`。CoAPはメッセージIDで重複を検出し、二度目は破棄します。トークンが同じでも **メッセージIDが違えば別要求** なので混同注意。

### (5) 下線④：DTLSハンドシェークの偽装と攻撃名

| 項目 | 解答（40字以内） |
|---|---|
| 偽装の内容 | **送信元IPアドレスを，攻撃対象のホストのIPアドレスに偽装する。** |
| 攻撃名 | **リフレクション** |

小さな ClientHello を偽装して送ると、サーバが大きな ServerHello／証明書を「攻撃対象」へ返すため、増幅型の DDoS になります。DTLS 1.3 は最初の ClientHello をセッションに使わず、cookie を返して送信元の到達性を確認します。

### (6) 下線⑤：cookie検査の意味

| 項目 | 解答（各30字以内） |
|---|---|
| cookieが正しい場合に判断できること | **(ⅰ)の送信元が，偽装されたものでないこと** |
| cookieが不正な場合の対応 | **(ⅳ)を送信せず，ハンドシェークを終了する。** |

→ 正 cookie を持つ相手だけが実際にパケットを往復できた＝実在のクライアント、と確認できます。

## 設問4 IoTシステムの機能と構成

### (1) 下線⑥：ランダム送信の効果（35字以内）

**「Gメーター管理サーバやネットワークへの負荷の集中が避けられる。」**

数万台が「毎日0時ちょうど」に一斉送信するとサーバやネットワークに負荷が集中するため、0時〜1時のランダムな時刻に散らします（一般的な「ジッタ」の考え方）。

### (2) 下線⑦：スリープの効果（25字以内）

**「Gメーターの消費電力を抑えることができる。」**

要件②「電池で長時間稼働」に直結する解答です。

### (3) 下線⑧：HTTP/1.1ならIPパケットが多くなる理由（35字以内）

**「TCPコネクション確立とコネクション切断の処理が行われるから」**

CoAPはUDPなのでコネクション確立（3-way handshake）／切断が不要。検針データ24件を送るだけなら、その分のオーバヘッドが丸ごと削れます。

### (4) 下線⑨：DTLS不要と判断した理由（30字以内）

**「CoAP通信は，Y社向けの閉域網の中で行われるから」**

Z社のLPWA閉域接続サービス＋IPsec VPNで他社・インターネットから隔離されているため、暗号化しなくても機密性が確保できる、という判断です。

### (5) 下線⑩：時刻誤差で発生する問題（30字以内）

**「測定と送信が誤った時刻に行われることになる。」**

1時間ごとの測定時刻と「毎日0時測定→ランダム送信」のタイミングがずれ、集計時に「どの時間帯のデータか」が壊れます。

### (6) 下線⑪：時刻誤差を抑えるCoAP通信（40字以内）

**「Gメーター管理サーバから現在時刻を取得して，Gメーターの時刻を更新する。」**

図9のとおりY社拠点のサーバはNTPで時刻同期済み。GメーターはCoAPでそのサーバから時刻を取得すれば、高精度RTCを全台に載せるより安価に誤差を抑えられます。

# まとめ：この問題で問われた「合格の要点」

1. **IPv6の「対応関係」を理解する**
   - ARP↔NS/NA、DHCP↔RS/RA(SLAAC)、TTL↔ホップリミット、NAPT↔GUA直接＋FW
2. **LLAとGUAの使い分け**
   - 同一リンク制御（OSPFv3ネクストホップ）＝LLA、外部通信・識別＝GUA
3. **「なぜ？」を字数制限内で書く力**
   - 「ロンゲストマッチ」「ホップリミットが0になるまで」「トークン値が一致する」など、キーワードを先に置く
4. **CoAPは「メッセージID＝重複検出」「トークン＝要求の対応付け」**
   - ここを混同すると設問3(2)(3)(4)が連鎖的に落ちる
5. **IoT設計は「省電力・負荷分散・閉域性・時刻同期」の4軸で考える**
   - スリープ／ランダム送信／DTLS不要／NTP＋CoAP時刻取得

> 解答例の字数は「上限」なので、短くてもキーワードが入っていればOK。逆に長く書くと減点対象になるため、答案用紙の枠を意識してまとめましょう。
