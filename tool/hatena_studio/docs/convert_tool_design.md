## 1. 背景と目的

### 1.1 背景

ネットワークスペシャリスト試験の解答・解説記事は、Markdown で執筆したうえで、はてなブログの「HTML 編集モード」に貼り付ける HTML へ変換している。この変換はもともと Python スクリプト `md_to_hatena.py` で行っていたが、次の課題があった。

- 記事ごとにコマンドライン引数を組み立てる必要がある。
- 変換結果の確認には、出力 HTML をブラウザで開く操作が別途必要になる。
- 関連記事の再選定（特定記事の除外）やキャッシュ更新のたびに、コマンドを打ち直す必要がある。
- 変換オプションや前回の入力ファイルがセッションをまたいで保持されない。
- 記事ファイルの選択を毎回パス入力で行う必要がある。

### 1.2 目的

既存の Python 版と同等の変換結果を保ちながら、日常的に使える GUI を持つ Rust アプリケーションにする。

達成目標:

1. Markdown を選んでボタン 1 つで変換し、その場でプレビューできる。
2. 関連記事の確認・除外・再選定、フィードキャッシュ更新を GUI から行える。
3. 生成した HTML をそのままクリップボードへコピーできる。
4. 従来のバッチ利用もできるよう、ワンショット CLI を残す。
5. はてなブログのテーマ CSS に依存しない HTML を出力する。
6. JavaScript が無効でも記事として読める。
7. 有料サービス・外部 AI API を使わず、ローカル処理だけで完結する。

### 1.3 非目標

- はてなブログへの自動投稿・下書き保存（API 連携は行わない）。
- 記事本文の生成や校正（変換と装飾のみ）。
- 複数ユーザーでの同時利用、インターネット公開。
- Python 版の完全な撤去（比較用の参照実装として残す）。

### 2.3 制約

- UI は Rust で実装する（ユーザー要望）。
- UI 形態はローカル Web UI とする。
- はてなブログの HTML 編集モードに貼り付けられる断片を出力する。
- 記事本文の全文転載は行わない（問題文の著作権に配慮）。
- 既存の Python 版とキャッシュ JSON を共有できる形式にする。

### 2.4 受け入れ条件

1. 代表記事 `R6_pm2_解答解説.md` がエラーなく変換できる。
2. 主要なタグ数・本文テキストが Python 版と一致する（同一キャッシュ条件）。
3. GUI から変換・プレビュー・コピー・関連記事除外・キャッシュ更新ができる。
4. JS 無効時にも本文が読める。
5. `cargo test` が全件成功し、ビルド警告がない。

## 3. 設計方針（意思決定の記録）

| ID | 決定 | 検討した代替案 | 理由 |
| --- | --- | --- | --- |
| D-01 | UI はローカル Web UI | ネイティブ GUI（egui / Tauri） | HTML プレビューとの相性がよく、UI を HTML/CSS/JS で迅速に作れる。Rust 側は axum に集中できる |
| D-02 | HTTP サーバは axum | actix-web、warp | 型安全でルーティングが簡潔。Tokio エコシステムと統合しやすい |
| D-03 | Markdown 解析は pulldown-cmark | comrak、自作パーサ | CommonMark 準拠でイベント API が扱いやすい。GFM 表・打消し線・タスクリストに対応 |
| D-04 | イベントから独自 AST を構築 | HTML 文字列を直接加工 | 見出し補正・目次・関連記事挿入などの後処理を構造的に行える |
| D-05 | 関連記事 HTML はビルド時に静的埋め込み | 閲覧時に JS でフィード取得 | はてな側で JS が制限されても関連記事が表示される。CORS も不要 |
| D-06 | フィードキャッシュは Python 版と互換 JSON | 独自形式 | どちらのツールで更新しても同じキャッシュを共有できる |
| D-07 | 埋め込み JS は記事内に直接挿入 | 外部ファイル参照 | はてなブログの HTML 編集モードで完結する |
| D-08 | JS はプログレッシブエンハンスメント | JS 必須の UI | 検索エンジン・RSS・JS 無効環境でも本文が読める |
| D-09 | ワンショット CLI を維持 | GUI のみ | 定常運用と CI 的な検証の両方を可能にする |
| D-10 | 設定は APPDATA 配下 | 作業フォルダ内 | 複数の記事フォルダを切り替えても設定を共有できる |
| D-11 | フィードは先頭 3000 文字のみ類似度に使用 | 全文使用 | 解析時間とメモリを抑えつつ、主題判定には十分 |
| D-12 | 有料サービス・外部 AI は使わない | クラウド類似度 API | コスト・可用性・記事内容の外部送信を避ける |

### 4.2 プロセスと状態

- 単一プロセス。axum の非同期ランタイム上で HTTP を処理する。
- Markdown 変換は CPU バウンドのため `spawn_blocking` で実行し、ランタイムを塞がない。
- 直近の変換結果（プレビュー HTML・はてな用断片・出力パス）はメモリ上の `Latest` に保持する。再起動すると消える。
- 設定とフィードキャッシュはディスクに永続化する。

### 4.3 主要なデータフロー

#### 変換

```
Markdown 選択
  → POST /api/convert
  → 入力解決（相対パスは作業フォルダ基準）
  → BOM 除去
  → 先頭 H1 をタイトルとして分離（任意）
  → pulldown-cmark でイベント列へ
  → 独自 AST へ変換
  → 見出し補正・メタ情報・クイズ・関連記事・目次
  → インラインスタイル付き HTML へ描画
  → `<元名>_hatena.html` と `<元名>_preview.html` を保存
  → レスポンス（統計・ログ・関連記事・キャッシュ状態）
  → iframe にプレビュー表示
```

#### 関連記事

```
GET /api/convert
  → キャッシュが有効なら読み込み
  → 無効/更新指定なら Atom フィード取得（最大 N ページ）
  → 記事と候補をトークン化
  → TF-IDF コサイン + キーワード一致 + タイトル加点
  → スコア降順・上位 K 件
  → 関連記事 HTML を本文末尾へ挿入
```

## 6. Markdown 変換設計

### 6.1 パイプライン

`build_fragment` は次の順序で処理する。この順序は Python 版の後処理を再現するために重要である。

1. **入力正規化**: BOM を除去する。
2. **タイトル分離**: コードフェンス外の最初の `# ` をタイトルとして抜き出す。`--keep-title` 時は本文に残す。
3. **イベント解析**: `pulldown-cmark` で CommonMark イベント列を得る。
4. **AST 構築**: `Block` / `Inline` の独自 AST へ変換する。
5. **見出し補正**: 本文中に H1 が現れたら以降を 1 段下げる。「付録」「Appendix」の H3 は H2 に上げる。
6. **メタ情報カード**: 先頭の「対象：」「問題：」段落を 1 つのカードにまとめる。
7. **VXLAN クイズ挿入**: 「図4の対応表」見出しの直前に挿入する（オプション）。
8. **関連記事挿入**: 本文末尾に H2「関連記事」とカード群を追加する。
9. **見出し ID**: H2〜H4 に `sec-1`, `sec-2`, … を付与する。
10. **目次挿入**: H2/H3 を対象に TOC を生成し、最初の見出しの直前へ挿入する。
11. **HTML 描画**: すべての要素にインラインスタイルを付けて描画する。
12. **JS 埋め込み**: `hatena_interactive.js` を `<script>` として末尾に付加する。
13. **プレビュー生成**: 記事タイトルと紙面風スタイルでラップした完全な HTML を作る。

### 6.2 AST

代表的なブロック:

- `Paragraph`（通常段落 / リスト内の裸テキスト）
- `Heading`
- `Quote`
- `List`（順序付き・順序なし、入れ子）
- `Code`
- `Table`
- `Html`
- `Rule`
- `Meta`（対象・問題のカード）

代表的なインライン:

- `Text`, `Code`, `MathExpr`, `MathDisplay`, `Emphasis`, `Strong`, `Strikethrough`, `Link`, `Image`, `SoftBreak`, `HardBreak`

### 6.3 はてなブログ向けの出力方針

- 外部 CSS に依存せず、主要要素へ `style="..."` を直接付ける。
- 本文全体を `div[data-hatena-article="1"]` で包み、基準フォント・行間・折り返しを指定する。
- H2 は青のグラデーション帯、H3 は下線、H4 は左ボーダー。
- 「解答：」で始まる段落は緑のコールアウトにし、`data-answer="1"` を付ける。
- 「採点講評」で始まる段落は黄色のコメントにし、クイズ機能の対象にする。
- 強調だけの段落は青いラベルとして扱う。
- 表は `overflow-x:auto` のラッパーで包み、列数が多い場合は注意書きを付ける。
- コードブロックは濃色背景・等幅フォント・横スクロール。
- 数式ははてなブログの tex 記法 `[$ ... $]` で出力する。`$...$` はインライン、`$$...$$` は `\displaystyle` を付けた中央寄せブロックにし、はてな側の MathJax で描画させる。この記法は LaTeX をエスケープせずに書ける。
- 見出しには `scroll-margin-top` を付け、目次リンクで移動したときに隠れないようにする。

### 6.4 Python 版との互換のための補正

#### 日本語の助詞前の強調

CommonMark の right-flanking 規則では、`**LSDB（…）**を` のように直後が日本語の助詞である強調が解釈されない場合がある。Python 版の結果に合わせるため、連続する `Text` ノードを結合したうえで `**…**` を `Strong` へ補正する。

#### リスト項目・表セルの裸テキスト

`pulldown-cmark` はリスト項目内のテキストを `Paragraph` で包まない場合がある。そのままでは本文が消えるため、`Paragraph { bare: true }` として描画する。表セルも同様にインライン列を直接解析する。

#### 入れ子リスト

2 スペースインデントの入れ子リストは CommonMark では入れ子として扱われる。Python-Markdown は同じ入力をフラットな項目にすることがあるが、本アプリは **CommonMark 準拠の入れ子を正** とし、テストで固定している。

## 7. 関連記事設計

### 7.1 フィード取得

- URL: `<blog_url>/feed?page=N`
- 1 ページあたりの件数はフィード側の仕様に依存（実測 30 件/ページ）。
- 既定の最大ページ数は 15。1〜50 にクランプする。
- ページ取得ごとに 100ms 待機し、相手サイトへの負荷を抑える。
- URL の重複を排除する。
- 途中ページで失敗した場合は警告を出して打ち切る。1 ページ目の失敗はエラー。
- 1 記事あたり:
  - `summary`: 先頭 1500 文字
  - `content`: HTML をプレーンテキスト化し、先頭 3000 文字
  - `published` が空なら `updated` を使う

### 7.2 キャッシュ

- 既定パス: `<記事フォルダ>/.hatena_feed_cache.json`
- 形式: `blog_url`, `fetched_at`（Unix 秒）, `entries`
- 有効期間: 既定 12 時間
- キャッシュが有効で `refresh=false` ならフィードへアクセスしない。
- 取得に失敗した場合:
  1. ブログ URL が一致するキャッシュがあれば使う。
  2. なければ関連記事セクションだけを省略する。
- 取得結果が空だった場合も、キャッシュがあれば使う。
- Python 版と同一形式のため、相互に更新可能。

### 7.3 正規化とトークン化

- NFKC 正規化 + 小文字化。
- ASCII 語: `[a-z0-9][a-z0-9+#._/-]*`、長さ 2〜32。
- 日本語: 連続する日本語文字（ひらがな・カタカナ・漢字）を 2 文字ずつに分割したバイグラム。
- 検索ノイズ除去のため、目次プレフィックスや BGM 表記を除外する。

### 7.4 スコア式

記事ドキュメント:

```
title × 4 + headings × 3 + body × 1
```

候補ドキュメント:

```
title × 4 + categories × 3 + summary × 1 + content_text × 2
```

TF-IDF:

```
tf-idf(t) = (1 + ln(tf(t))) × idf(t)
idf(t)    = ln((1 + N) / (1 + df(t))) + 1
```

`N` は候補数 + 1（記事自身を含む）。

類似度:

```
cosine = コサイン類似度(記事ベクトル, 候補ベクトル)
```

ドメインキーワード:

- あらかじめ定義した `DOMAIN_KEYWORDS`（VXLAN、EVPN、OSPF、SPF、DKIM など）の出現集合を使う。
- キーワード IDF は `ln((1 + 候補数) / (1 + 出現候補数)) + 1`。
- IDF 重み付き Jaccard:

```
keyword_score = Σ idf(共通キーワード) / Σ idf(和集合)
```

タイトル加点:

```
title_bonus = 0.10 × min(記事と候補タイトルの共通トピック語数, 2)
```

最終スコア:

```
score = 0.68 × cosine
      + 0.32 × keyword_score
      + title_bonus
      + 0.02（カテゴリに「ネットワーク」を含む場合）
```

### 7.5 候補の除外

- URL が空、タイトルが空の記事は除外。
- 記事自身は、タイトルを NFKC 正規化・空白除去したうえで完全一致するものを除外。
- GUI で「×」された URL は `exclude_urls` として除外。
- `score < min_score`（既定 0.02）は除外。
- スコア降順、同点なら公開日の新しい順。
- 既定 5 件、最大 20 件。

### 10.2 状態管理

`app.js` の `state` が次を保持する。

- 除外 URL の集合

- プレビュー URL

- 変換中: ボタン無効化・スピナー表示・二重実行防止
- トースト: 成功・警告・エラーを画面右下に表示

- デスクトップ: サイドバー + ビューアの 2 カラム。

- 320px でも横スクロールが出ないことを検証済み。
- iframe 内の記事は幅 100% で表示し、表・コードは内部スクロールにする。

### 10.5 アクセシビリティ

- タブに `role="tab"` / `aria-selected`。
- キャッシュ状態に説明用 `title`。
- ファイルブラウザはフォーカス可能なボタンで構成。

- iframe に `title`。
- JS 無効でも本文は読める。

## 14. 既知の差分・制約・今後の課題

### 14.1 既知の差分

- 2 スペースインデントの入れ子リストは、Python 版と HTML 構造が異なる。Rust 版は CommonMark 準拠で入れ子にする。
- 関連記事のスコアはフィードの記事数・内容に依存するため、キャッシュ更新後に変動する。

### 14.2 制約

- ローカル利用前提。認証がないため、ポートを外部公開しない。
- はてなブログへの自動投稿は行わない。生成 HTML を手動で貼り付ける。
- 生成 HTML はインラインスタイルと埋め込み JS のため約 200KB になる。貼り付け先のサイズ上限に注意する。
- フィードの 1 ページあたりの件数はブログ側の仕様に依存する。
- フィードキャッシュは記事本文の先頭 3000 文字を含むため、ファイルサイズが大きい。
- GUI の検証は Windows + Chromium を中心に行っている。macOS/Linux のファイルオープン処理はコード上分岐しているが、実機検証は未実施。

### 14.3 今後の候補

- リリースビルドの配布用パッケージ化（exe + assets）。
- 記事ごとのプリセット保存。
- 変換前後の差分表示。
- 関連記事の手動ピン留め・並べ替え。
- はてなブログの下書き API 連携（認証情報の管理が必要）。
- 複数記事の一括変換。
- キャッシュの圧縮・差分更新。
- macOS/Linux での GUI 検証。
